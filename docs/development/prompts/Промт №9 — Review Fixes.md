Определи ближайшее действие по замечаниям независимого ревью текущего PR проекта `vbondarev/intelligence.trade.system`. Используй актуальные инструкции репозитория и `.agents/skills/trade-system-pr-review/SKILL.md`. На этапе №9 анализируй замечания и готовь материалы для владельца или coding-agent. Исполнение исправлений выполняется отдельным действием.

Сначала установи PR, исходный отчёт и проверенную версию. Для каждого замечания выясни, нужен ли обязательный FIX, утверждена ли его редакция, разрешено ли исполнение, опубликовано ли изменение и состоялась ли независимая проверка.

**Режим А — спроектировать FIX.** Если способ исправления ещё предстоит определить, выполни применимые проверки §1–10. Подготовь перечень FIX, доказательства, регрессионные проверки и вопросы владельцу. Если точная редакция уже подготовлена и ожидает утверждения, представь её с указанием требуемого решения. При запросе владельца приложи проект исполнительского задания и обозначь, что именно ещё требует согласования.

**Режим Б — подготовить задание по согласованным FIX.** Сверь применимость решения и действующий WHAT/HOW по §1–3 и §10. Сформируй и проверь самостоятельное задание по §11–12. Для уже подготовленного актуального задания достаточно указать его редакцию и ближайшее действие. Отдельно зафиксируй, дал ли владелец разрешение на передачу и исполнение.

**Если исправление опубликовано**, свяжи замечание с изменением и HEAD. При отсутствии требуемой независимой проверки укажи №10. Если проверка уже состоялась, используй её результат в пределах проверенной версии. При существенном изменении исходных условий назови затронутые FIX и выводы, требующие обновления.

Выбирай режим по каждому замечанию. Выполняй последующие разделы в объёме, необходимом для этого режима.

## 1. Определение текущего PR

Если номер PR указан явно, используй его.

Если номер не указан:

1. Восстанови текущий PR из результатов последнего External Review.
2. Определи связанный GitHub Issue.
3. Проверь, что PR соответствует текущей задаче и утверждённому Implementation Plan.
4. Убедись, что отсутствует неоднозначность между несколькими PR.

Не выбирай произвольный PR.

Если текущий PR уже слит или закрыт, установи его фактический статус и не подготавливай обычную инструкцию по изменению закрытого PR без отдельного решения.

## 2. Восстановление контекста

Получай необходимые сведения непосредственно из GitHub.

Изучи:

- текущий PR и его метаданные;
- актуальные head и base SHA;
- полный текущий diff;
- связанный Issue / WHAT;
- Base Approved Implementation Plan;
- все действующие Approved Plan Amendments;
- effective HOW;
- `AGENTS.md`;
- применимые локальные и path-specific instructions;
- ADR и contract docs;
- изменённые компоненты и их зависимости;
- существующие тесты;
- актуальные CI checks;
- Codex/Copilot reviews;
- inline review threads;
- последний External Review Report;
- реестр замечаний `ER-01 ... ER-N`.

Проверь доверенное авторство и действующие правила неизменяемости canonical HOW.

Если Issue, Approved Plan или Amendments недостоверны, не пытайся восстановить правильный вариант из предположений.

При критическом конфликте источников остановись.

## 3. Проверка актуальности External Review

Сравни текущее состояние PR с reviewed-state fingerprint последнего External Review.

Проверь:

1. PR number.
2. Head SHA.
3. Base SHA.
4. Связанный Issue.
5. Base Approved Plan permalink.
6. Список и порядок Amendments.
7. Effective HOW.
8. Существенные метаданные PR.
9. Актуальные reviews и threads.
10. CI текущего HEAD.

Если состояние не изменилось, используй предыдущий External Review как исходный набор замечаний, но самостоятельно проверяй каждое исправление по коду.

Если HEAD, BASE или effective HOW изменились, предыдущий review не считается подтверждением нового состояния.

В этом случае:

- определи характер изменений;
- получи актуальный код;
- повторно проверь затронутые findings;
- выяви новые существенные отклонения, если они появились;
- зафиксируй изменение reviewed-state fingerprint.

Если из-за изменения состояния невозможно достоверно использовать предыдущий отчёт, остановись и укажи необходимость нового External Review.

Не считай прежнее замечание актуальным только потому, что оно присутствует в отчёте.

## 4. Независимая проверка замечаний

Для каждого `ER-XX`:

1. Найди исходное замечание.
2. Определи нарушенное требование, контракт или инвариант.
3. Найди соответствующий текущий код.
4. Проверь фактическое поведение.
5. Подтверди или опровергни техническую проблему.
6. Проверь, не было ли замечание уже исправлено.
7. Установи наличие существующих тестов.
8. Проверь соответствующие Codex/Copilot comments и threads.
9. Определи необходимость изменения кода.
10. Классифицируй результат.

Используй статусы:

- `CONFIRMED` — дефект подтверждён и требует исправления.
- `ALREADY_FIXED` — замечание уже устранено текущим кодом.
- `INVALID` — замечание технически необоснованно.
- `OBSOLETE` — замечание относится к устаревшей реализации.
- `DUPLICATE` — замечание дублирует другое.
- `NEEDS_EVIDENCE` — доказательств недостаточно.

Для `CONFIRMED` дополнительно укажи `BLOCKER` или `NON_BLOCKER`.

Не создавай исправление для `INVALID`, `OBSOLETE` или `DUPLICATE` без самостоятельного технического основания.

Не считай `ALREADY_FIXED` доказанным без проверки соответствующего кода.

Не объявляй `NEEDS_EVIDENCE` исправленным.

## 5. Анализ первопричин

Для каждого подтверждённого дефекта самостоятельно установи:

**Ожидаемое поведение**

- Что должно происходить согласно WHAT и HOW.
- Какие инварианты необходимо сохранять.

**Фактическое поведение**

- Что реализовано неправильно.
- В каких условиях проявляется ошибка.

**Первопричина**

- Какой конкретный механизм вызывает проблему.
- Почему существующая реализация не соответствует требованиям.
- Какие зависимости влияют на дефект.

**Последствия**

- Какие сценарии нарушаются.
- Какие данные или компоненты могут пострадать.
- Существует ли риск регрессий.
- Как дефект влияет на Acceptance Criteria.

**Недостатки тестирования**

- Почему существующие тесты не выявляют проблему.
- Какие проверки отсутствуют или недостаточно строгие.

Не поручай coding-agent повторно выполнять этот анализ.

Не ограничивайся формулировкой «исправить ошибку».

Установи конкретную техническую причину и способ её устранения.

## 6. Классификация необходимых изменений

Для каждого подтверждённого дефекта определи одну из категорий.

### LOCAL_FIX

Исправление полностью соответствует существующим WHAT и effective HOW.

Оно не требует:

- изменения утверждённой архитектуры;
- замены согласованного алгоритма;
- изменения scope;
- пересмотра обязательных контрактов;
- нового существенного решения.

Такое исправление может быть подготовлено к исполнению coding-agent после моего утверждения перечня Review Fixes.

### HOW_CHANGE_REQUIRED

Для устранения дефекта необходимо изменить утверждённый технический подход.

Примеры:

- замена алгоритма;
- изменение ответственности компонентов;
- пересмотр согласованной последовательности обработки;
- изменение утверждённых механизмов хранения или согласованности.

Не включай такое изменение в исполнимый набор LOCAL_FIX.

Подготовь обоснование и направь вопрос на процедуру №7 — STOP → Human Decision → Approved Plan Amendment.

### WHAT_CHANGE_REQUIRED

Для исправления необходимо изменить требования, scope или Acceptance Criteria.

Не изменяй Issue самостоятельно.

Подготовь обоснование и направь вопрос на Human Decision с последующим обновлением WHAT и, если требуется, HOW.

### SOURCE_CONFLICT

Невозможно достоверно установить действующий WHAT/HOW либо существует конфликт утверждённых источников.

Приостанови подготовку зависящих от конфликта исправлений до разрешения проблемы.

### MISSING_EVIDENCE

Недостаточно данных для определения первопричины или безопасного способа устранения.

Укажи конкретные недостающие доказательства.

Не передавай coding-agent задачу самостоятельно выбирать решение при отсутствии данных.

Если отдельные LOCAL_FIX не зависят от блокирующих вопросов, можешь подготовить их отдельно, явно указав границы независимости.

## 7. Проектирование исправлений

Для каждого подтверждённого `LOCAL_FIX` самостоятельно разработай точное техническое решение.

Используй идентификаторы:

`FIX-01`, `FIX-02`, `FIX-03` и далее.

Для каждого FIX укажи:

### Идентификатор и связь с finding

Например:

`FIX-01 → ER-03`

Если одно исправление устраняет несколько взаимосвязанных findings, укажи все соответствующие идентификаторы.

### Техническая проблема

Кратко опиши дефект и установленную первопричину.

### Цель исправления

Определи конкретный ожидаемый результат.

### Затронутые компоненты

Укажи подтверждённые:

- пути существующих файлов;
- классы и методы;
- интерфейсы;
- модели;
- тестовые проекты;
- необходимые зависимости.

Новые файлы обозначай как планируемые.

Не выдумывай существующие компоненты.

### Точные технические изменения

Самостоятельно определи:

1. Что необходимо изменить.
2. Как именно должна работать исправленная логика.
3. Какие условия и алгоритмы использовать.
4. Какие существующие механизмы сохранить.
5. Как обработать негативные и пограничные случаи.
6. Какие действия запрещены.
7. Как обеспечить совместимость с остальной реализацией.

Не оставляй coding-agent выбор архитектурной альтернативы или нового существенного алгоритма.

### Сохраняемые инварианты

Перечисли обязательные архитектурные, доменные и технические ограничения.

### Тестирование

Определи конкретные тестовые сценарии и ожидаемые результаты.

### Критерии завершения

Укажи объективные условия, по которым можно подтвердить исправление.

### STOP-условия

Определи обстоятельства, при которых coding-agent обязан остановиться.

Если исправление требует изменения Approved Plan, не представляй его как готовое к исполнению.

## 8. Последовательность исправлений

Проанализируй зависимости между FIX.

Определи:

- какие исправления независимы;
- какие необходимо выполнить раньше других;
- какие затрагивают общие компоненты;
- какие могут вызвать повторную регрессию;
- какие тесты нужно запускать после отдельных изменений;
- какие проверки необходимо выполнить после полного набора FIX.

Не создавай искусственную декомпозицию на несколько PR.

По умолчанию все утверждённые Review Fixes должны выполняться в существующей рабочей ветке и существующем PR.

Если технически необходимо разделение, представь обоснование для моего рассмотрения.

Не разрешай coding-agent самостоятельно создавать новый PR вместо текущего.

## 9. Проектирование регрессионных тестов

Для каждого FIX определи тесты, которые должны доказать устранение первопричины.

Укажи:

1. Исходные условия.
2. Входные данные.
3. Последовательность выполнения.
4. Ожидаемый результат.
5. Проверяемый инвариант.
6. Негативные и пограничные случаи.
7. Какие предыдущие сценарии не должны измениться.

Если применимо, предусмотрите регрессионный тест, который обнаруживает исходный дефект.

Не ограничивайся проверкой, что код компилируется.

Не принимай успешный CI как достаточное доказательство исправления логической ошибки.

Проверь достаточность существующей тестовой инфраструктуры.

Не предлагай новые тестовые зависимости без необходимости.

## 10. Сохранение WHAT/HOW

Для каждого предлагаемого исправления проверь:

- соответствие Issue;
- соответствие effective Approved Plan;
- отсутствие scope expansion;
- сохранение архитектурных границ;
- отсутствие несогласованных изменений API/contracts;
- отсутствие побочных продуктовых изменений;
- сохранение требований безопасности;
- отсутствие несвязанного рефакторинга.

Построй матрицу:

`ER Finding → Root Cause → FIX → Affected IMP/AC → Regression Test`

Если исправление меняет утверждённый HOW, не включай его в исполнимую инструкцию до прохождения процедуры Amendment.

Промт Review Fixes не является новым Implementation Plan.

Он конкретизирует устранение дефектов в пределах уже утверждённого решения.

## 11. Подготовка инструкции coding-agent

После завершения анализа сформируй **полный самостоятельный технический промт для coding-agent**, предназначенный для исполнения после моего утверждения.

Он должен содержать:

### Контекст

- Repository.
- Номер и permalink существующего PR.
- Связанный Issue.
- Base Approved Plan permalink.
- Все применимые Amendments.
- Текущий проверенный head SHA.
- Base branch.
- Рабочую ветку PR.

### Объём исправлений

Точный перечень утверждаемых `FIX-01 ... FIX-N`.

Не включай необоснованные, устаревшие или дублирующие findings.

### Последовательность действий

Для каждого FIX:

- точные компоненты;
- конкретные изменения;
- предусмотренные алгоритмы;
- обязательные инварианты;
- тестовые сценарии;
- критерии завершения;
- STOP-условия.

### Проверки

Предписанные:

- сборки;
- unit/integration/contract tests;
- регрессионные тесты;
- применимые Docker/smoke checks;
- проверка документации;
- основной self-review;
- финальный self-review;
- CI.

### Git

Обязательно укажи:

- использовать существующую ветку и PR;
- не создавать новый PR без отдельного разрешения;
- не изменять WHAT/HOW;
- не изменять архитектуру;
- не расширять scope;
- сохранить согласованные правила commit;
- выполнить commit и push после обязательных проверок;
- обновить PR description, если это необходимо для отражения фактических исправлений и актуальных ссылок на HOW;
- выполнить PR sanity check.

Commit message должен соответствовать формату:

`#<issue>: <текст на русском языке в прошедшем времени>`

### Итоговый отчёт исполнителя

Потребуй:

- перечень выполненных FIX;
- изменённые файлы;
- добавленные тесты;
- результаты проверок;
- commit SHA;
- новый head SHA;
- ссылку на существующий PR;
- статус CI;
- невыполненные проверки и препятствия.

### Ограничения coding-agent

Coding-agent:

- исполняет утверждённые исправления;
- не проверяет повторно обоснованность External Review как самостоятельный ревьюер;
- не выбирает альтернативную архитектуру;
- не меняет утверждённый HOW;
- не расширяет scope;
- не подменяет предписанный алгоритм собственным;
- не удаляет обязательные тесты;
- не выполняет самостоятельный Re-review;
- не разрешает review threads без отдельного указания;
- не выполняет merge.

Разреши локальную диагностику и исправление ошибок собственной реализации в пределах утверждённых FIX и HOW.

При невозможности точного исполнения — STOP и фактический отчёт.

Не поручай coding-agent самостоятельно определить, какие замечания нужно исправлять и каким способом.

## 12. Проверка подготовленного задания

Перед представлением исполнительского промта самостоятельно проверь:

1. Все включённые findings действительно подтверждены.
2. Каждому FIX соответствует установленная первопричина.
3. Нет лишних или дублирующих исправлений.
4. Указанные существующие компоненты подтверждены кодом.
5. Все технические решения достаточно конкретны.
6. Все необходимые тесты предусмотрены.
7. FIX не нарушают друг друга.
8. Требования и инварианты сохраняются.
9. Задание не изменяет WHAT/HOW без согласования.
10. Coding-agent не должен самостоятельно выполнять архитектурный анализ.
11. Существующий PR и ветка определены однозначно.
12. Команды проверки соответствуют репозиторию.
13. STOP-условия достаточны.
14. Исполнительский промт не зависит от истории предыдущего чата.

Если обнаружен недостаток, исправь его до представления результата.

Не заменяй отсутствующие факты предположениями.

## 13. Формат результата

Начни с общего статуса и одного ближайшего действия по PR. Укажи PR, HEAD и исходное ревью.

Для каждого существенного замечания дай одну строку:

`ER/RR → FIX или решение владельца → состояние и доказательство → ближайшее действие`.

Если требуется решение владельца, назови точную редакцию или вопрос. Если требуется задание coding-agent, включи цель, согласованные FIX, границы WHAT/HOW, проверки и условие остановки. Отдельно укажи состояние разрешения на исполнение.

Для опубликованных исправлений достаточно ссылок на изменения, проверяемого HEAD и предмета независимого Re-review.

| Статус | Текст определения |

| `READY_FOR_HUMAN_APPROVAL` | Редакция конкретных FIX подготовлена и ожидает утверждения. Укажи, что именно владелец должен рассмотреть. |
| `ASSIGNMENT_PREPARED` | Задание по согласованным FIX готово. Укажи, ожидается ли разрешение владельца или исполнение уже разрешено. |
| `READY_FOR_RE_REVIEW` | Все обязательные исправления, требуемые на этом шаге, опубликованы и ожидают независимой проверки. Укажи HEAD и замечания для №10. |
| `NO_FIXES_REQUIRED` | На этапе №9 обязательной работы по исправлению не осталось, и нет опубликованных обязательных FIX, ожидающих независимой проверки. Укажи основание и следующий применимый этап. |
| `BLOCKED_BY_HUMAN_DECISION` | Продолжение зависит от конкретного решения владельца о границах, способе исправления или изменении WHAT/HOW. |
| `BLOCKED_BY_MISSING_DATA` | Отсутствует конкретное доказательство, необходимое для выбора или проверки исправления. |
| `REVIEW_REFRESH_REQUIRED` | Существенное изменение состояния PR лишило соответствующий вывод исходного ревью актуальности. Укажи, какую часть ревью требуется обновить. |
| `BLOCKED_BY_SOURCE_CONFLICT` | Между действующими источниками WHAT/HOW выявлено противоречие, влияющее на исправление. |

**Правило смешанного результата.** Если все обязательные FIX опубликованы и ожидают независимой проверки, общий статус — `READY_FOR_RE_REVIEW`. Согласованные неблокирующие отсрочки перечисли отдельно. Если хотя бы один обязательный FIX ещё требует решения, подготовки или исполнения, выбери общий статус по ближайшему действию, которое продвигает обязательную работу. В строках отдельных замечаний сохрани остальные состояния. Если препятствие блокирует только один FIX, укажи, какие независимые действия по остальным уже доступны.
