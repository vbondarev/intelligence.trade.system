- предусмотренную техническую защиту;
- необходимое тестирование;
- условие, при котором coding-agent должен остановиться.

Разделяй:

**LOCAL IMPLEMENTATION DEFECT**

Ошибка собственной реализации, устранимая coding-agent строго в пределах утверждённого HOW.

**HOW CHANGE REQUIRED**

Необходимость изменить утверждённый способ реализации. Требуется STOP, анализ ChatGPT и новый Human Gate с Amendment.

**WHAT CHANGE REQUIRED**

Необходимость изменить требования или scope. Требуется STOP, Human Decision и обновление Issue до изменения HOW.

**MISSING DATA / CONFLICT**

Недостаточные сведения или противоречие источников, из-за которого невозможно безопасно продолжать работу.

Coding-agent не должен самостоятельно переклассифицировать проблему, требующую нового архитектурного решения, в локальное исправление.

3. Все существенные технические изменения имеют основание в WHAT.
4. Все обязательные сценарии имеют способ проверки.
5. Нет незапланированного расширения scope.
6. Нет неутверждённых архитектурных решений.
7. Не осталось неопределённых технических решений, которые придётся принимать coding-agent.
8. Все STOP-условия имеют понятные основания.
9. Зависимости между шагами и PR согласованы.

Если обнаружен пробел, исправь план в пределах своих полномочий.

Если устранение пробела требует моего решения, не подменяй его предположением.

## 15. Самопроверка Implementation Plan

Перед представлением результата проведи критическую техническую самопроверку полного плана.

Оцени его с позиции coding-agent, который:

- не имеет доступа к истории нашего чата;
- работает исключительно по утверждённым документам и исполнительскому заданию;
- не уполномочен самостоятельно выбирать архитектурные альтернативы;
- может обладать более ограниченными аналитическими возможностями.

Проверь:

**Архитектура**

- Корректен ли выбранный подход.
- Сохраняются ли инварианты.
- Используются ли существующие механизмы.
- Нет ли скрытых изменений контрактов.

**Исполнимость**

- Можно ли выполнить шаги в заданном порядке.
- Достаточно ли конкретны технические действия.
- Нет ли неразрешённых архитектурных вопросов.
- Проверены ли предполагаемые существующие компоненты.

**Полнота**

- Все требования покрыты.
- Нет пропущенных шагов.
- Все необходимые тесты предусмотрены.
- Документация учтена.

**Риски**

- Есть ли опасные пограничные сценарии.
- Не нарушаются ли безопасность и согласованность данных.
- Корректно ли определены STOP-условия.

**Границы**

- Не расширяется ли scope.
- Не противоречит ли план Issue.
- Не принимаются ли решения за человека.
- Не передаётся ли аналитическая ответственность coding-agent.

Исправь найденные недостатки, если это допустимо без нового Human Decision.

Не объявляй план готовым, если остаются существенные неразрешённые вопросы.

## 16. Формат Implementation Plan

Представь полный самостоятельный документ со следующей структурой.

### 1. Паспорт плана

- Repository.
- Issue и permalink.
- Связанный этап ROADMAP.
- Целевая ветка.
- Исследованный HEAD SHA.
- Версия Implementation Plan.
- Статус `PROPOSED`.
- Основания и применимые источники.

### 2. Цель и границы реализации

Краткое изложение согласованного WHAT, scope и out-of-scope без замены самого Issue.

### 3. Фактическое техническое состояние

Существующие компоненты, механизмы, зависимости и ограничения.

### 4. Архитектура предлагаемого решения

Компоненты, ответственность, взаимодействия, алгоритмы и сохраняемые инварианты.

### 5. Технические решения

Выбранные подходы, обоснование и соответствие существующим утверждённым решениям.

### 6. Изменения компонентов

Конкретные существующие и планируемые файлы, классы, интерфейсы, контракты и механизмы.

### 7. Последовательность реализации

Полные шаги `IMP-01 ... IMP-N`.

### 8. Декомпозиция PR

Если применимо — границы, зависимости и проверяемые результаты каждого PR.

### 9. Стратегия тестирования

Конкретные тестовые сценарии, обязательные проверки и ожидаемые результаты.

### 10. План документации

Документы и необходимые изменения.

### 11. Риски и STOP-условия

Риски, защиты, классификация проблем и условия остановки.

### 12. Ограничения coding-agent

Чёткие границы самостоятельности исполнителя.

### 13. Матрица прослеживаемости

`Requirement → AC → IMP → PR → Test / Evidence`.

### 14. Human Decisions

Новые вопросы, требующие моего утверждения, если они обнаружены.

Отделяй их от решений, уже утверждённых в Issue, ADR или предыдущих Human Decisions.

### 15. Результаты самопроверки

Укажи результат самопроверки для версии плана и исследованного HEAD из паспорта. Для покрытия WHAT сошлись на матрицу прослеживаемости из подпункта 13. Перечисли обнаруженные пробелы, существенные ограничения и открытые решения с указанием затронутого AC, IMP или PR. Если блокеров не выявлено, зафиксируй это прямо. Различай наличие запланированной проверки и доказательство, которое предстоит получить при её выполнении.

### 16. Итоговый статус

Готовность к Human Gate.

Документ должен быть самодостаточным, последовательным и пригодным для дальнейшей подготовки технических заданий coding-agent без повторного архитектурного проектирования.

## 17. Итоговый статус

Используй один из статусов:

- `READY_FOR_HUMAN_GATE` — план технически проработан, все существенные решения определены, блокирующих вопросов нет.
- `BLOCKED_BY_HUMAN_DECISION` — требуется моё продуктовое или архитектурное решение.
- `BLOCKED_BY_MISSING_DATA` — невозможно достоверно завершить проектирование из-за недостатка критических данных.

Статус `READY_FOR_HUMAN_GATE` означает готовность плана к моему рассмотрению, а не автоматическое утверждение.

До моего явного согласия план остаётся `PROPOSED`.

### Что дальше в ответе

В конце ответа выбери одно ближайшее действие по фактическому результату и учти уже выполненные шаги и явные разрешения. Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. Помещай подсказку после результата, за пределами публикуемого артефакта и задания исполнителю. Подсказка служит текстом для владельца, полномочия определяет его поручение.

Для полной редакции плана дай команду проверить её по №5.1, указав Issue, версию и границу «пока не публикуй и не начинай реализацию». При блокировке назови конкретное решение владельца или недостающий источник.

## 18. Ограничения и ответственность

**Ты (ChatGPT):**

- исследуешь существующий код;
- анализируешь архитектуру;
- проектируешь техническое решение;
- определяешь алгоритмы и компоненты;
- формируешь последовательность реализации;
- проектируешь тестирование;
- выявляешь риски;
- выполняешь самопроверку;
- представляешь Implementation Plan для утверждения.

**Я:**

- принимаю новые существенные архитектурные и продуктовые решения;

- прохожу Human Gate;
- разрешаю публикацию Approved Implementation Plan;
- разрешаю последующий переход к реализации.

**Coding-agent:**

- не участвует в техническом проектировании;
- не выбирает архитектурные альтернативы;
- не формирует Implementation Plan;
- не принимает самостоятельные решения, изменяющие WHAT/HOW;
- подключается только на этапе исполнения подготовленного технического задания.

Не изменяй код, тесты или документацию.

Не редактируй Issue, ROADMAP или ADR.

Не создавай рабочие ветки, коммиты или Pull Request.

Не публикуй Implementation Plan в GitHub до Human Gate и отдельного разрешения на публикацию.

Не передавай задачу coding-agent.

Не начинай implementation.
