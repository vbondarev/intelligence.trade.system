## 4. Подготовка GitHub Issue

Используй актуальный шаблон:

`.github/ISSUE_TEMPLATE/development-task.md`

Сохраняй предусмотренную им структуру, обязательные разделы и Definition of Done.

### Название

Сформулируй краткое и конкретное название на русском языке.

Если задача соответствует этапу ROADMAP, используй его идентификатор.

Название должно описывать ожидаемый результат, а не последовательность программирования.

### Цель

Опиши:

- проблему, которую необходимо решить;
- ожидаемый результат;
- продуктовую или системную ценность.

Не описывай конкретный способ реализации.

### Контекст

Укажи:

- связь с ROADMAP;
- фактическое исходное состояние;
- необходимые зависимости;
- существенные архитектурные предпосылки;
- связанные Issue/PR;
- ссылки на применимые ADR и contracts.

Сохраняй только контекст, который необходим для самостоятельного понимания задачи.

### Требования

Перенеси все согласованные обязательные требования.

Для сложной задачи допускается использование идентификаторов `FR-01`, `FR-02` и далее.

Требования должны определять:

- обязательное поведение;
- ограничения;
- применимые нефункциональные характеристики;
- существенные негативные и пограничные сценарии;
- требования к совместимости, безопасности и достоверности данных.

Не добавляй новые требования без моего утверждения.

Не превращай предполагаемые технические решения в обязательные требования.

### Не входит в задачу

Явно обозначь out-of-scope:

- соседнюю функциональность;
- изменения будущих этапов;
- несогласованные расширения;
- действия, которые coding-agent не должен выполнять в рамках задачи.

Границы должны исключать неоднозначное расширение scope во время реализации.

### Архитектурные ограничения

Укажи специфичные для задачи утверждённые ограничения.

Ссылайся на существующие ADR/contracts.

Если в Human Decisions принято новое архитектурное решение, отрази его согласованный смысл.

Не добавляй архитектурные решения, которые я не утверждал.

Не подменяй архитектурные ограничения подробным техническим проектированием.

### Критерии приёмки

Сформулируй объективные и проверяемые Acceptance Criteria.

Для сложной задачи допускается использование идентификаторов `AC-01`, `AC-02` и далее.

Каждый критерий должен:

- соответствовать конкретному требованию;
- описывать наблюдаемое поведение или проверяемое свойство;
- быть однозначным;
- иметь понятный способ проверки;
- учитывать существенные негативные и пограничные сценарии;
- не предписывать внутренний алгоритм без утверждённого архитектурного основания.

Не добавляй численные показатели или гарантии, отсутствующие в согласованных требованиях и действующих контрактах.

### Тестирование

Определи, какие виды проверок необходимы для подтверждения требований.

Укажи применимые:

- модульные тесты;
- интеграционные тесты;
- API/contract tests;
- регрессионные сценарии;
- проверки безопасности;
- проверки конкурентности и идемпотентности;
- эксплуатационные и другие специфичные проверки.

Определяй, что должно быть проверено, но не проектируй конкретную реализацию тестовой инфраструктуры.

Если определённый вид проверки неприменим, укажи причину.

### Документация

Определи, какие документы должны быть созданы или обновлены в результате выполнения задачи.

Учитывай действующие README, ROADMAP, ADR/contracts, API docs и инструкции репозитория.

Не требуй изменения документов без связи с согласованной задачей.

### Definition of Done

Сохрани актуальный Definition of Done из шаблона Issue.

Не удаляй и не ослабляй существующие обязательные требования к:

- Human Gate;
- Approved Implementation Plan;
- implementation;
- self-review;
- tests/checks;
- документации;
- External Review;
- Re-review;
- Human Merge Gate.

Не дублируй эти правила в других разделах Issue без необходимости.

## 5. Граница WHAT / HOW

GitHub Issue должен отвечать на вопросы:

- Что необходимо реализовать?
- Какое поведение ожидается?
- Какие требования обязательны?
- Какие ограничения необходимо соблюдать?
- Что не входит в задачу?
- Как установить, что результат соответствует требованиям?

Issue не должен самостоятельно определять:

- последовательность программирования;
- перечень создаваемых методов и классов;
- внутренние алгоритмы без утверждённого основания;
- техническую декомпозицию по файлам;
- конкретные commit;
- рабочие ветки;
- детальное содержание будущих PR.

Эти вопросы относятся к Implementation Plan.

Исключение составляют технические решения, уже утверждённые человеком или закреплённые действующими архитектурными контрактами.

Не подменяй будущий HOW преждевременным проектированием.

Самостоятельно проверь перенос согласованного WHAT в Issue.

Сформируй внутреннюю матрицу:

`Discovery Requirement / Human Decision → Issue Requirement → Acceptance Criterion`

Проверь:

1. Каждое согласованное обязательное требование отражено в Issue.
2. Все применимые Human Decisions учтены.
3. Нет новых неутверждённых требований.
4. Scope и out-of-scope согласованы.
5. Каждый существенный Requirement имеет способ проверки.
6. Acceptance Criteria покрывают обязательное поведение.
7. Нет критериев, противоречащих требованиям.
8. Архитектурные ограничения соответствуют ADR/contracts.
9. Не включён несогласованный HOW.
10. Все необходимые зависимости обозначены.


Если обнаружен существенный пробел, не заполняй его предположением.

## 8. Самопроверка Issue

Перед представлением результата проведи независимую самопроверку подготовленного текста.

Проверь:

**Полноту**

- Все требования и решения учтены.
- Нет потерянных Acceptance Criteria.
- Указаны необходимые зависимости.

**Корректность**

- Требования соответствуют утверждённому Discovery.
- Нет противоречий между разделами.
- Архитектурные ограничения согласованы с действующими решениями.

**Проверяемость**

- Критерии приёмки объективны.
- Существенные сценарии покрыты.
- Не предполагается недоступное или непроверяемое доказательство выполнения.

**Scope**

- Отсутствуют несогласованные расширения.
- Out-of-scope обозначен достаточно точно.
- Не включены соседние задачи ROADMAP.

**WHAT / HOW**

- Нет преждевременного технического проектирования.
- Все обязательные технические ограничения имеют утверждённое основание.

**Самостоятельность документа**

- Новый агент сможет восстановить WHAT непосредственно из GitHub.
- Issue не зависит от истории предыдущего чата.
- Все существенные внешние источники доступны по ссылкам.

**Соответствие шаблону**

- Сохранены обязательные разделы и Definition of Done.
- Соблюдена языковая политика проекта.

Исправь найденные недостатки, которые можно устранить без изменения утверждённых решений.

Не принимай за меня новые продуктовые или архитектурные решения.

## 10. Итоговый статус

Используй один из статусов:

- `READY_FOR_PUBLICATION_APPROVAL` — Issue полностью подготовлен и может быть представлен мне на утверждение.
- `BLOCKED_BY_HUMAN_DECISION` — обнаружены существенные вопросы, требующие моего решения.
- `BLOCKED_BY_MISSING_DATA` — не хватает критических данных для достоверного формирования WHAT.
