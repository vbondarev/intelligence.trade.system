## 1. Восстановление утверждённого плана

Определи:

1. Номер и permalink связанного Issue.
2. Последнюю явно утверждённую версию Implementation Plan.
3. Полный утверждённый текст.
4. Факт прохождения Human Gate.
5. Исследованный HEAD SHA.
6. Утверждённые архитектурные решения и ограничения.

Не восстанавливай утверждённую редакцию по памяти или сокращённому пересказу.

Если полный текст либо факт утверждения невозможно достоверно подтвердить, остановись.

## 2. Проверка перед публикацией

Повторно получи состояние GitHub Issue и применимых источников.

Проверь:

- правильность Issue;
- явное разрешение владельца на публикацию именно этой утверждённой редакции. Одно сообщение может подтвердить утверждение и публикацию, если оба действия названы явно;
- отсутствие уже опубликованного canonical Base Approved Plan;
- отсутствие конфликтующих решений;
- соответствие утверждённого HOW согласованному WHAT;
- отсутствие существенных изменений, требующих повторного Human Gate.

Если разрешение на публикацию ещё требуется, остановись после подтверждения статуса утверждения. Если Base Approved Plan уже опубликован, не создавай второй базовый план.

Если необходимо изменить существующий HOW, используй отдельную процедуру Approved Plan Amendment после Human Decision.

Не редактируй существующие канонические комментарии.

## 3. Подготовка канонического документа

Первая строка опубликованного комментария должна быть строго:

`# Approved Implementation Plan`

Далее размести полный утверждённый Implementation Plan.

Сохрани:

- номер Issue;
- версию плана;
- исследованный HEAD;
- все технические решения;
- архитектуру;
- шаги IMP;
- декомпозицию PR;
- тестирование;
- документацию;
- матрицу требований;
- риски и STOP-условия;
- ограничения coding-agent.

Служебный статус опубликованного плана — `APPROVED`.

Не оставляй в канонической публикации противоречивые статусы `Proposed` или `ожидает Human Gate`.

Допускаются только технические изменения оформления, явно разрешённые при утверждении: добавление канонического заголовка и приведение служебного статуса к `APPROVED`.

Не переписывай, не сокращай и не дополняй утверждённое техническое содержание.

Если требуется содержательное изменение, остановись и верни документ на Human Gate.

Проверь:

1. Комментарий принадлежит правильному Issue.
2. Первая строка точно равна `# Approved Implementation Plan`.

## 7. Неизменяемость

После успешной публикации Base Approved Implementation Plan считается неизменяемым по правилам проекта.

Не редактируй и не удаляй его.

GitHub технически допускает редактирование комментариев, поэтому проверка доступных метаданных не является абсолютным доказательством исторической неизменности.

Изменения утверждённого HOW должны проходить отдельный Human Decision и новый Human Gate.

Для таких изменений используется append-only комментарий:

`# Approved Implementation Plan — Amendment`

Не создавай Amendment в рамках текущей публикации.

- Base Approved Implementation Plan permalink.

**Проверка**

- Результат проверки уникальности Base Plan.
- Доступные признаки неизменяемости.

**Итоговый статус**

- `APPROVED_PLAN_PUBLISHED` — план опубликован и проверен.
- `PUBLICATION_VERIFICATION_FAILED` — публикация выполнена, но необходимые проверки не пройдены.
- `PUBLICATION_BLOCKED` — публикацию невозможно безопасно выполнить.

При `PUBLICATION_BLOCKED` или `PUBLICATION_VERIFICATION_FAILED` не разрешай переход к implementation.
