# №12 — Проверка готовности к Human Merge Gate

Независимо проверь, готов ли текущий PR к решению владельца о слиянии. Проверь реализацию, актуальность ревью, обязательные условия GitHub и документацию, которая окажется в целевой ветке. По умолчанию работай в режиме чтения. Если владелец явно разрешил условное снятие Draft с конкретного PR, действуй по §6. Разрешение на ручное слияние оформляется отдельно по №13.

## 1. Восстанови состояние PR

Установи repository, PR, Issue, целевую ветку, HEAD/BASE, доверенный Approved Plan и все действующие Amendments либо основание `N/A`. Для `N/A` сверь связь PR с Issue, проверяемое разрешение и ограничения маршрута по `trade-system-pr-review`. Проверь применимые инструкции, карточку №11, исходный независимый отчёт, полный текущий diff, документацию, CI, reviews, threads, approvals, Draft и mergeability.

GitHub подтверждает состояние объектов и версий. Отчёт подтверждает охват независимой проверки. Решения владельца устанавливай по сообщению или артефакту, позволяющему определить их границы.

Если карточка №11 недоступна, восстанови ожидаемый результат по Issue, применимому основанию, критериям и исходному отчёту. Недостающие доказательства укажи явно.

## 2. Проверь WHAT, HOW и объём завершения

Сопоставь реализацию с критериями текущего PR и действующим HOW. Отдельно установи, завершает ли PR весь Issue, конкретный пункт ROADMAP и родительский этап.

Для ранее блокировавших findings проверь исправление и независимую перепроверку. Для отложенных пунктов укажи решение владельца и его границы. Новые обязательства и исключения требуют соответствующего утверждённого основания.

## 3. Установи исходное независимое ревью

Определи роль проверяющего, охват, технический вывод и проверенную пару HEAD/BASE. Допустим отчёт, явно принятый владельцем как первичный External Review, в пределах фактически проверенного.

Если отчёт мог существовать, проверь доступные ссылки и относящийся к задаче чат. Если основание осталось неизвестным, укажи `UNVERIFIED`. Если установлено, что первичного ревью не было, ближайший шаг — №8. Отзывы ботов и CI учитывай по их назначению.

## 4. Определи объём повторной проверки

**A. Проверенное состояние сохранилось.** Используй прежние доказательства в их границах. Актуальный положительный №8 без обязательных FIX достаточен как исходное ревью для маршрута №11 → №12. Обнови сведения о CI, замечаниях, approvals и mergeability.

**B. После №11 изменились только документы, BASE прежняя.** Подтверди исходное независимое ревью, сравни прежний и новый HEAD, затем проверь полный текущий diff относительно актуальной BASE. Для содержательной правки зафиксируй: `было → стало → пункт WHAT/HOW → подтверждение реализации → вывод`.

Если правка уточняет уже утверждённые WHAT/HOW и сохраняет критерии приёмки, выполни независимую проверку внутри №12 §4B. Проверь основание правки, дельту, полный текущий diff, затронутые выводы, прежние blockers, актуальные HEAD/BASE и обязательный CI для текущего HEAD. Если BASE изменилась или изменилось техническое поведение, примени §4C. Если ошибочен только текст, выдай `NOT_READY` и верни точную правку в №11.

Если новая формулировка меняет обязательное поведение, зависимость, исключение или критерий, назови расхождение. При открытом решении владельца передай в №7.1 прерванное действие и источник препятствия.

**C. Существенно изменилось проверенное состояние.** Определи влияние изменения BASE, кода, тестов, контракта, конфигурации или effective HOW. При установленном исходном ревью и незавершённой обязательной перепроверке — `STALE_REVIEW`. После опубликованных FIX укажи №10, вход А. После существенного изменения без FIX — №10, вход Б. При смешанном случае передай обе причины.

## 5. Проверь ROADMAP как отдельное условие допуска

Прочитай основную строку каждого затронутого пункта непосредственно из текущего HEAD PR. Сверь её с карточкой №11 и утверждёнными критериями. Проверь связанные сводки, родительский этап, следующий пункт и зависимости.

Для каждого пункта заполни:

| Пункт ROADMAP | Ожидается в целевой ветке после merge | Фактически в основной строке HEAD | Сводки и зависимости | PASS / FAIL / UNVERIFIED | Ссылка на версию |
|---|---|---|---|---|---|

Применяй правила:

- Критерии выполнены, а основная строка или действующая сводка оставляет пункт «в работе» — `FAIL`, итог `NOT_READY`, возврат в №11 с точным местом исправления.
- Пункт отмечен завершённым преждевременно — `FAIL`. Укажи незакрытый критерий.
- PR частичный, открытый пункт и остаток отражены правильно — `PASS` для документации. Укажи отдельный результат по объёму PR.
- Критерий проверяется только после merge — подтверди основание, промежуточный статус, событие, исполнителя и последующее обновление. Если критерий обязателен до merge, перенос блокирует допуск.
- Нужная версия или основание недоступны — `UNVERIFIED`. Назови недостающую информацию.
- Нужное состояние уже было в документе — допустим `PASS` со ссылкой на фактическую строку.

При параллельных изменениях ROADMAP в BASE установи, что в результате слияния сохранятся нужные строки обеих веток. Используй доступный merge candidate или проверяемое сравнение версий. При подтверждённом конфликте укажи препятствие. При недостатке свидетельств не ставь `PASS`.

## 6. Проверь остальные условия допуска

Проверь сопутствующую документацию, описание и labels PR, ссылки на Issue и применимое основание, фактическое покрытие AC и ожидаемое действие с Issue. Существенные утверждения в Issue и PR должны соответствовать текущей фазе работы.

Заполни блок «Версии и CI» из `trade-system-pr-review` для каждого обязательного запуска, на который опирается допуск. Сверь применимость результата к текущему HEAD и вершине целевой ветки. Если BASE события отличается, проверь охват классификации и фактический checkout применимых заданий. Отдельно укажи подтверждённые ограничения GitHub. При недостающем доказательстве положительный допуск невозможен. Проверь допустимость `skipped`. Проверь актуальные замечания Codex/Copilot, unresolved threads, required approvals, branch protection, Draft, конфликты и доступность merge.

### Условное снятие Draft

1. Проверь все условия допуска, кроме Draft. Переход к записи возможен для открытого Draft PR, если владелец явно разрешил снятие Draft для этого PR и все остальные обязательные условия подтверждены для проверенной пары HEAD/BASE. При ожидаемом обязательном CI, другом препятствии или недостающем доказательстве сохрани Draft и назови причину.
2. Непосредственно перед снятием Draft повторно прочитай PR и вершину целевой ветки из GitHub. Для этой сверки HEAD — текущий SHA PR, BASE — SHA вершины целевой ветки. Если Draft уже снят, переходи к финальной сверке без записи. Если HEAD или BASE изменились, сохрани Draft до конца текущего прохода, даже при разрешении для PR без SHA. Обнови затронутые выводы в режиме чтения и покажи новую пару для следующей проверки №12. При разрешении на конкретную пару учитывай его границы. Если пара сохранилась, а изменилось другое существенное условие, перепроверь его и повтори последнюю сверку перед записью.
3. При подтверждённых условиях сними Draft и перечитай PR из GitHub. Подтверди `isDraft=false`, текущие HEAD/BASE, основание реализации, обязательный CI, approvals, review threads и mergeability. Если состояние изменилось после записи, примени §4 и обнови затронутые выводы. Положительный итог допустим по подтверждённому состоянию после финальной сверки. При ошибке действия укажи фактический статус PR.

## 7. Зафиксируй результат

Перед вердиктом повторно получи HEAD/BASE и существенные условия допуска. При изменении вернись к §4 и перепроверь затронутые выводы, включая ROADMAP. Если PR уже слит, передай в №14 факт и время merge, последнюю проверенную пару и сведения о допуске, зафиксированном до слияния.

Выдай паспорт версий, краткое заключение по WHAT/HOW и ревью, построчные результаты ROADMAP, состояние Issue, CI, threads, approvals и mergeability. Выбери один итог:

- `READY_FOR_HUMAN_MERGE_GATE` — обязательные условия подтверждены для финальной пары HEAD/BASE, карточка описывает корректное состояние после merge.
- `NOT_READY` — есть конкретное препятствие. Укажи его, способ устранения и ближайший этап.
- `UNVERIFIED` — отсутствуют данные, необходимые для заключения.
- `STALE_REVIEW` — прежнее ревью установлено, но требуемая проверка изменившегося состояния ещё не выполнена.

При положительном допуске зафиксируй проверенную пару, карточку и ссылки на доказательства для №13. В рамках №12 допустимо условное снятие Draft по §6. Остальные изменения файлов и состояния GitHub требуют отдельного поручения. Решение о merge принимает владелец по №13.

## Что дальше в ответе

В конце ответа выбери одно ближайшее действие по фактическому результату и учти уже выполненные шаги и явные разрешения. Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. Помещай подсказку после результата, за пределами публикуемого артефакта и задания исполнителю. Подсказка служит текстом для владельца, полномочия определяет его поручение.

При положительном допуске предложи №13 для проверенной пары HEAD/BASE. При `NOT_READY` назови первое действие по фактическому препятствию. Если единственное препятствие — Draft и разрешения ещё нет, предложи команду «Разрешаю снять Draft с PR #… при неизменных HEAD/BASE, если Draft — единственное препятствие. После снятия заверши №12 и остановись перед №13». Если HEAD или BASE изменились до записи, укажи новую пару и предложи следующий запуск №12. Если разрешённое действие не удалось, укажи причину и подтверждённое состояние PR. При `STALE_REVIEW` или `UNVERIFIED` назови проверку или доказательство, необходимое для актуального допуска.
