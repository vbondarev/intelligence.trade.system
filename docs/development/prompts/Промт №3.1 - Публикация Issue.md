
Утверждаю последнюю согласованную редакцию GitHub Issue для текущей задачи проекта `vbondarev/intelligence.trade.system`.

Разрешаю опубликовать именно эту редакцию с утверждёнными названием, содержимым и labels.

## 1. Проверка перед публикацией

Перед созданием:

1. Восстанови точную утверждённую версию Issue.

2. Убедись, что моё явное согласование относится именно к этой редакции.

3. Проверь наличие уже созданного Issue. Если эквивалентная публикация существует, продолжи с её номером и сверкой по §3.

4. Проверь актуальность существенных источников и отсутствие новых противоречий. Для проверки labels используй действующие labels репозитория и правила Discovery.

5. Убедись, что публикация не добавляет новых требований или решений.

6. Проверь утверждённые labels по `trade-system-discovery`: ровно один действующий `type:*` и минимум один применимый `area:*`. При пустом наборе назови обе недостающие категории. При пропуске категории или нескольких `type:*` назови конкретный дефект и останови публикацию до согласования полной классификации.


Если утверждённую редакцию невозможно достоверно восстановить, остановись.

Если обнаружен существенный конфликт, не изменяй согласованный WHAT самостоятельно. При повторной сверке существующего Issue без доступной утверждённой редакции назови, какое доказательство нужно восстановить для подтверждения публикации.

## 2. Публикация

Создай GitHub Issue в репозитории `vbondarev/intelligence.trade.system`.

Используй точные утверждённые:

- название;

- Markdown-содержимое;

- labels.


Не заменяй утверждённую редакцию сокращённым пересказом.

Не изменяй требования и Acceptance Criteria.

Не создавай дублирующий Issue, если эквивалентная публикация уже существует.

## 3. Проверка после публикации

Повторно получи созданный Issue непосредственно из GitHub.

Проверь:

1. Номер и permalink.

2. Название.

3. Полноту Markdown-содержимого.

4. Наличие всех обязательных разделов.

5. Соответствие требованиям и Acceptance Criteria.

6. Совпадение фактического набора labels с утверждённым и наличие обязательных категорий. При повторной сверке используй существующий номер Issue. При несовпадении перечисли недостающие и лишние labels; при неполной классификации назови конкретный пробел.

7. Отсутствие случайных изменений согласованного WHAT.


При выявлении ошибки сообщи о расхождении.

Техническую ошибку публикации можно исправить только без изменения согласованного смысла. Содержательные изменения требуют моего утверждения.

## 4. Результат

Верни:

- номер Issue;

- permalink;

- заголовок;

- labels;

- результат сверки с утверждённой редакцией;

- обнаруженные проблемы, если есть.


Итоговый статус:

- `ISSUE_PUBLISHED_VERIFIED` — Issue успешно создан и проверен.

- `PUBLICATION_VERIFICATION_FAILED` — публикация или проверка завершилась ошибкой.


После успешной публикации Issue становится официальным источником истины для WHAT.

Не составляй Implementation Plan.

Не передавай задачу coding-agent.

Не изменяй код и документацию.

Не создавай ветку, коммиты и PR.

**После проверки публикации остановись на подсказке следующего действия. Выполнение следующего этапа требует применимого поручения.**

## Что дальше в ответе

Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. Помещай подсказку после результата, за пределами публикуемого артефакта и задания исполнителю. Подсказка служит текстом для владельца, полномочия определяет его поручение.

существующую Issue по номеру или ссылке. При блокировке публикации назови
условие, необходимое для продолжения.
