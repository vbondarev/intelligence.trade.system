# №14 — Проверка фактического результата после merge

Проверь результат слияния PR в целевую ветку. Установи, совпадают ли фактические состояния PR, Issue и конкретных пунктов ROADMAP с карточкой, проверенной до merge. По умолчанию работай в режиме чтения. По явному поручению владельца для конкретного Issue допустимо закрытие по §5. Поручение можно дать в команде запуска №14.

## 1. Установи факт и версию слияния

Получи из GitHub PR, Issue, признак `merged`, целевую ветку, время слияния, исходный HEAD PR, результирующий SHA и текущий HEAD целевой ветки. Учти способ слияния: merge commit, squash или rebase.

Если merge не подтверждён, сообщи установленное состояние и границу проверки. Одного `closed` для PR недостаточно.

## 2. Зафиксируй допуск, решение и факт отдельно

Для №12 установи, был ли до merge положительный допуск для слитого состояния. Для №13 установи, какое действие и в каких границах разрешил владелец. Для фактического merge укажи источник GitHub.

По №12 и №13 отдельно используй одну из формулировок:

- «подтверждено для слитого состояния»;
- «не подтверждено доступными источниками»;
- «установлено расхождение».

Укажи источник и время, если оно установлено. При пробеле назови недостающий артефакт. Продолжи доступные постпроверки. №12 и №13 задним числом не выполняются.

## 3. Сверь реализацию и документацию

Проверь, что согласованные изменения, обязательные FIX, тесты, конфигурация и сопутствующая документация вошли в целевую ветку. Используй результат слияния и фактическое содержимое файлов. Укажи основание проверки: доверенный Approved Plan с Amendments либо `N/A` по Issue и проверяемое разрешение владельца до реализации. Для `N/A` сверь в пределах слитого состояния условия `trade-system-pr-review` и зафиксируй пробелы отдельно от фактического результата. При squash или rebase учитывай изменение SHA.

## 4. Проверь каждый пункт ROADMAP в двух версиях

Возьми ожидаемый результат из карточки №11, проверенной №12. Если карточка недоступна, восстанови ожидание по Issue, действовавшему основанию и доказательствам приёмки, явно указав источник.

Сначала прочитай ROADMAP **на результирующем SHA слияния**. Для каждого затронутого пункта сверь основную строку, актуальную сводку, статус родителя и следующий пункт. Затем, если текущий HEAD целевой ветки отличается, проверь состояние этих мест сейчас.

| Пункт ROADMAP | Ожидалось при merge | Факт на SHA слияния и ссылка | Факт на текущем HEAD, если отличается | Расхождение и действие |
|---|---|---|---|---|

Различай три случая:

1. **Статус был неверен уже при merge.** Укажи точную строку, ожидаемое значение и основание. Для полностью выполненного пункта, оставленного «в работе», это `POST_MERGE_DISCREPANCY`.
2. **Статус был верен при merge и изменился позже.** Зафиксируй правильный результат проверяемого PR. Установи, было ли последующее изменение обоснованным. Ошибочную позднюю перезапись укажи как отдельное текущее расхождение.
3. **Промежуточный статус был предусмотрен.** Проверь согласованное событие. Пока обязательная проверка выполняется, назови её и условие продолжения. После положительного результата проверь, выполнено ли предусмотренное обновление ROADMAP и кто отвечает за остаток.

Если родительский этап по-прежнему имеет незавершённые критерии, его открытый статус корректен даже при полностью завершённом дочернем пункте.

## 5. Проверь CI и состояние GitHub

Раздельно покажи pre-merge CI и post-merge CI. Для обязательных запусков укажи SHA, ссылку, состояние и результат. Значение отменённого или пропущенного задания оцени по правилам workflow и итоговому обязательному check.

### Проверка и закрытие Issue

1. Прочитай фактическое состояние связанного Issue из GitHub. Сверь его с карточкой №11, обязательными критериями и подтверждённой поставкой. Полностью выполненный Issue подлежит закрытию. При частичной поставке укажи остаток и сохрани открытый статус. Строка `Closes #…` в описании PR сама по себе не подтверждает закрытие.
2. Если Issue уже `closed / completed`, подтверди результат без записи. При неожиданной причине закрытия или закрытии частичной задачи укажи расхождение. Исправление такого статуса требует отдельного поручения.
3. Если Issue открыт, закрой его с причиной `completed` только по явному поручению владельца для этого Issue. До действия подтверди merge в согласованную ветку, доставку всего обязательного объёма и выполнение условий закрытия из карточки №11. Если критерий закрытия отложен до post-merge проверки, дождись её результата. Обычный post-merge CI может ещё выполняться, если карточка допускает закрытие до его завершения. При установленном сбое обязательной проверки или существенном расхождении сохрани открытый статус и назови препятствие.
4. Непосредственно перед записью перечитай Issue из GitHub. Если он всё ещё открыт и условия соблюдены, закрой его. После действия снова прочитай Issue и подтверди `closed`, причину `completed` и время закрытия. Если подтверждения нет, сообщи наблюдаемый статус и причину.

Проверь административное завершение PR и соответствие описаний фактическому результату. Учитывай правила проекта о том, какие действия требуются после merge.

## 6. Выдай Post-Merge Report

Включи в отчёт:

1. PR, Issue, целевую ветку, время и SHA слияния.
2. Допуск №12 и решение №13 с их источниками.
3. Факт доставки согласованного объёма и обязательные результаты CI.
4. Построчную сверку ROADMAP.
5. Фактическое состояние Issue и оставшееся административное действие.
6. Итог по PR, отдельно — по всей задаче и родительскому этапу.
7. Одно ближайшее действие по запрошенному объекту.

Используй один итоговый статус и отдельно перечисли все существенные остатки:

- `POST_MERGE_VERIFIED` — согласованный результат данного PR доставлен, обязательные проверки пройдены, Issue и ROADMAP находятся в ожидаемом состоянии. Для частичного PR явно назови оставшуюся работу родительской задачи.
- `POST_MERGE_ACTION_REQUIRED` — после подтверждённого слияния осталось предусмотренное действие, например закрытие полностью завершённой Issue или согласованное обновление после наступления post-merge события.
- `POST_MERGE_PENDING` — обязательная последующая проверка ещё выполняется.
- `POST_MERGE_DISCREPANCY` — доказано существенное расхождение результата, документации, условий допуска или обязательных проверок.
- `POST_MERGE_UNVERIFIED` — для достоверного заключения недостаточно данных. Применяется также, когда единственный пробел — неподтверждённый обязательный допуск №12 или решение №13.

Если одновременно обнаружены подтверждённое существенное расхождение и пробел в истории допуска, укажи `POST_MERGE_DISCREPANCY` с его фактическим основанием. Пробел опиши отдельно.

В рамках №14 допустимо закрыть конкретный Issue по явному поручению на условиях §5. Остальные изменения GitHub и ROADMAP требуют отдельного поручения. Отдельно зафиксируй результат закрытия и результат post-merge CI. Пока обязательный CI выполняется, подтверждённое закрытие Issue допускает итог `POST_MERGE_PENDING`. Выдавай `POST_MERGE_VERIFIED` после подтверждения всех обязательных условий.

## Что дальше в ответе

В конце ответа выбери одно ближайшее действие по фактическому результату и учти уже выполненные шаги и явные разрешения. Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. Помещай подсказку после результата, за пределами публикуемого артефакта и задания исполнителю. Подсказка служит текстом для владельца, полномочия определяет его поручение.

Если результат подтверждён, покажи **Завершено** для запрошенного объекта. Для частичного PR отдельно укажи конкретный остаток родительской Issue. Если полностью выполненный Issue остался открытым и разрешения ещё нет, предложи команду «По №14 закрой Issue #… как completed, если подтверждены merge и полный объём поставки и выполнены условия закрытия. Перечитай Issue из GitHub и сообщи итог». При незакрытом критерии или расхождении ROADMAP назови одно действие по нему. Если закрытие подтверждено и остаётся post-merge CI, укажи ожидаемый запуск и команду повторной сверки.
