
Опубликуй последние утверждённые изменения WHAT и/или Approved Plan Amendment текущего Issue проекта `vbondarev/intelligence.trade.system`.

Human Gate для изменения HOW пройден.

Используй `AGENTS.md`, `.agents/skills/trade-system-delivery/SKILL.md` и правила доверенных канонических комментариев.

Цель — зафиксировать утверждённые изменения в GitHub и подтвердить, что coding-agent сможет однозначно восстановить действующие WHAT и HOW.

## 1. Проверка перед публикацией

Восстанови точные утверждённые редакции документов.

Проверь:

- правильный Issue;
- явное утверждение человеком;
- отсутствие несогласованных изменений;
- актуальность Base Approved Plan;
- доверенность и неизменяемость предыдущих Amendments;
- отсутствие уже опубликованного эквивалентного Amendment;
- отсутствие новых существенных конфликтов.

Если публикация не может быть выполнена без изменения утверждённого содержания, остановись.

## 2. Публикация WHAT

Если утверждены изменения WHAT:

1. Обнови только согласованные разделы GitHub Issue.
2. Сохрани не затронутые решением требования.
3. Повторно прочитай Issue из GitHub.
4. Сверь опубликованную редакцию с утверждённой.
5. Проверь Acceptance Criteria и границы scope.
6. Зафиксируй permalink и результат проверки.

Не изменяй другие Issue и ROADMAP без отдельного утверждённого основания.

Если обновление WHAT не удалось или опубликованное содержимое отличается от утверждённого, не переходи к публикации зависимого Amendment.

## 3. Публикация HOW

Если утверждён Approved Plan Amendment:

1. Проверь, что требуемые изменения WHAT уже успешно опубликованы.
2. Подготовь полный утверждённый текст Amendment.
3. Убедись, что первая строка строго равна:

`# Approved Implementation Plan — Amendment`

4. Укажи каноническую ссылку:

`Base Approved Implementation Plan: <permalink>`

5. Сохрани точное содержание утверждённых изменений.
6. Опубликуй Amendment отдельным GitHub Issue comment.
7.  Добавь ссылку в PR на Amendment.

Канонический Amendment должен быть опубликован доверенным пользователем `vbondarev` с `author_association=OWNER`.

Если доступные инструменты не позволяют обеспечить требуемое авторство, не публикуй комментарий от другого пользователя.

В таком случае предоставь готовый текст для ручной публикации.

Не редактируй Base Plan или ранее опубликованные Amendments.

## 4. Проверка после публикации

Повторно прочитай опубликованные артефакты непосредственно из GitHub.

Для Amendment проверь:

- принадлежность правильному Issue;
- точный канонический заголовок;
- автора `vbondarev`;
- `author_association=OWNER`;
- доступные признаки неизменяемости, предусмотренные workflow;
- ссылку на правильный Base Plan;
- полное соответствие утверждённому тексту;
- отсутствие дубликатов;
- корректный порядок применения Amendments.

Получение permalink само по себе не считается подтверждением успешной публикации.

Если публикация выполнена владельцем вручную, сначала получи и проверь фактический комментарий в GitHub.

## 5. Проверка effective HOW

После публикации восстанови:

`Base Approved Implementation Plan + все доверенные действующие Amendments`

Проверь:

1. Соответствие актуальному WHAT.
2. Отсутствие противоречий.
3. Однозначность заменённых положений.
4. Корректность последовательности IMP.
5. Актуальность тестов и STOP-условий.
6. Возможность самостоятельного восстановления плана coding-agent из GitHub.

Если опубликованные источники существенно противоречат друг другу, укажи конфликтующие положения и конкретное действие, которое остаётся заблокированным.

## 6. Результат

Представь:

- Issue и permalink;
- опубликованные изменения WHAT, если применимо;
- Base Approved Plan permalink;
- новый Amendment permalink, если применимо;
- автора и результат проверки доверия;
- все действующие Amendments в порядке применения;
- результат проверки effective HOW.

**Возврат к прерванной работе**

1. Укажи, какое действие потребовало поправки: реализация шага IMP, подготовка или исполнение FIX, независимое ревью, документальная правка либо проверка допуска. Назови связанный Issue, PR и замечание, если применимо.
2. Укажи, какое препятствие сняла опубликованная поправка и какие ограничения сохранились.
3. Для каждого затронутого замечания различай три факта: изменение допустимо по действующим WHAT/HOW; конкретный FIX утверждён; владелец разрешил его исполнение. Одно сообщение владельца может подтверждать несколько фактов. Укажи его предмет и границы. Для замечаний, уже покрытых базовым планом, сохрани ссылку на исходное основание.
4. Проверь, что произошло после принятия решения: подготовлено ли задание, опубликовано ли исправление, проверен ли новый HEAD. Назови первое оставшееся действие и исполнителя.
5. Рекомендуй №7.5, если возобновляется остановленная реализация. Для review fix выбери подготовку, исполнение или независимую проверку по его фактическому состоянию. Если владелец принял уже существующее техническое состояние, укажи требуемую проверку по обновлённому HOW.

Итоговый статус:

- `APPROVED_CHANGES_PUBLISHED_VERIFIED` — все необходимые изменения опубликованы и проверены.
- `PARTIALLY_PUBLISHED` — опубликована только часть утверждённых изменений. Перечисли проверенные артефакты, недостающий результат и ближайшее действие по публикации. Перед повторной попыткой сверь фактическое состояние GitHub, чтобы не создать дубликат. Возврат к прерванной работе возможен после подтверждения всей требуемой публикации.
- `PUBLICATION_BLOCKED` — безопасная публикация невозможна.
- `PUBLICATION_VERIFICATION_FAILED` — проверка опубликованных изменений не пройдена.

Не объявляй успех до завершения всех обязательных проверок.

### Что дальше в ответе

В конце ответа выбери одно ближайшее действие по фактическому результату и учти уже выполненные шаги и явные разрешения. Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. Помещай подсказку после результата, за пределами публикуемого артефакта и задания исполнителю. Подсказка служит текстом для владельца, полномочия определяет его поручение.

При полной проверенной публикации дай команду на первое оставшееся действие по прерванной работе. Укажи IMP, FIX, DOC или проверку, к которой нужно вернуться. При частичной публикации сначала предложи сверить существующие артефакты и завершить недостающую публикацию в пределах разрешения.

## 7. Ограничения

Не изменяй утверждённое техническое содержание.

Не редактируй прежние канонические комментарии.

Не изменяй код или тесты.

Не создавай ветки, коммиты или PR.

Не передавай coding-agent новый Implementation Plan.

Не выполняй implementation.

Не выполняй merge.

Представь статус публикации, ссылки на проверенные артефакты и ближайшее действие. Заверши №7.4 выдачей этого отчёта.
