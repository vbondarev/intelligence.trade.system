
Проведи полноценный независимый технический External Review текущего Pull Request проекта `vbondarev/intelligence.trade.system`.

Используй актуальные инструкции репозитория и workflow `.agents/skills/trade-system-pr-review/SKILL.md`.

**Твоя роль — независимый технический архитектор и ведущий разработчик, ответственный за проверку корректности реализации.**

Ты (ChatGPT) самостоятельно исследуешь исходный код, проверяешь архитектуру, бизнес-логику, требования, контракты, тесты, CI и замечания других ревьюеров. Выявляешь дефекты, устанавливаешь их технические причины и формируешь обоснованное заключение.

Я рассматриваю результаты External Review и принимаю решения, требующие моего участия.

Coding-agent на этом этапе не участвует. Он не анализирует замечания, не классифицирует их и не выбирает способы исправления.

**Цель этапа** — независимо от self-review coding-agent установить, соответствует ли текущая реализация утверждённым WHAT и HOW, выявить подтверждённые недостатки и подготовить проверяемый External Review Report для следующего этапа разработки.

Работай исключительно в режиме анализа.

## 1. Определение Pull Request

Если номер PR явно указан в моём сообщении, используй его.

Если номер не указан:

1. Восстанови текущую задачу разработки из доступного контекста.
2. Определи связанный GitHub Issue.
3. Найди соответствующий PR.
4. Проверь его связь с согласованным основанием исполнения.
5. Убедись, что рассматриваемый PR определяется однозначно.


Не выбирай произвольный PR на основании даты создания, номера или последней активности.

Если Issue содержит несколько PR, установи конкретную часть утверждённой реализации, которую необходимо проверить.

Не проверяй соседние PR вместо текущего.

Если PR уже слит или закрыт, явно установи это обстоятельство и не представляй исторический анализ как актуальную предслияльную проверку.

## 2. Восстановление источников истины

Получи необходимые сведения непосредственно из GitHub.

Обязательно изучи:

- текущий PR, его описание и метаданные;
- head и base branches;
- полный head SHA;
- полный base SHA;
- связанный GitHub Issue;
- требования, scope, out-of-scope и Acceptance Criteria;
- effective HOW, включая Base Approved Implementation Plan и действующие Amendments, либо основание `N/A`;
- ROADMAP.md;
- корневой и применимые локальные AGENTS.md;
- path-specific instructions;
- применимые ADR и contract docs;
- полный diff PR;
- существующие тесты;
- актуальные CI checks;
- Codex/Copilot reviews, comments и inline threads.

Не полагайся только на PR description или отчёт coding-agent.

Отделяй утверждения исполнителя от самостоятельно подтверждённых фактов.

## 3. Проверка доверенного WHAT/HOW

На обычном маршруте проверь:

1. PR связан с правильным Issue.
2. Issue однозначно определяет WHAT.
3. Base Approved Implementation Plan принадлежит этому Issue.
4. Его первая строка соответствует каноническому заголовку.
5. Автор Base Plan — `vbondarev` с `author_association=OWNER`.
6. Доступные метаданные подтверждают соблюдение правил неизменяемости.
7. Все применимые Amendments опубликованы доверенным автором.
8. Каждый Amendment ссылается на правильный Base Plan.
9. Все действующие Amendments учтены в порядке комментариев Issue.
10. Effective HOW восстанавливается однозначно.
11. В PR отсутствуют неутверждённые изменения WHAT/HOW.

Проверяй применимые метаданные `created_at` и `updated_at` согласно действующим правилам репозитория.

Помни, что совпадение временных отметок является проверкой установленного процесса, но не абсолютным криптографическим доказательством исторической неизменности.

Если canonical artifact изменён, отсутствует, недоверен или effective HOW невозможно восстановить, зафиксируй workflow blocker.

Для `N/A` проверь по `trade-system-pr-review` связь PR с Issue, точечный проверяемый объём, отсутствие доверенных плана и Amendments, а также явное разрешение владельца до реализации. Зафиксируй `N/A`, ссылку на Issue и доказательство разрешения. Применимые технические проверки и отдельный Human Merge Gate обязательны.

Не выбирай самостоятельно, какой конфликтующий вариант HOW считать правильным.

Если действующие правила требуют определённого формата связи PR с Issue, проверь его. При конфликте между форматом PR и утверждённой декомпозицией на несколько PR зафиксируй противоречие, а не изменяй правила самостоятельно.

## 4. Проверка полноты исходного кода

Перед техническим анализом убедись, что получен полный состав изменений.

Проверь:

- все изменённые файлы;
- добавленные файлы;
- удалённые файлы;
- изменения конфигурации;
- тестовые изменения;
- изменения документации;
- зависимости затронутых компонентов.

Не ограничивайся сокращённым diff или текстовым описанием PR.

Если необходимо, самостоятельно исследуй:

- полный код изменённых классов и методов;
- вызывающий код;
- зависимые сервисы;
- интерфейсы;
- доменные модели;
- repository implementations;
- миграции;
- тестовые фикстуры;
- DI-регистрации;
- конфигурацию.

Исследуй связанные компоненты настолько глубоко, насколько необходимо для проверки корректности изменённого поведения.

Если часть существенного кода недоступна, явно зафиксируй ограничение.

Не утверждай, что выполнен полный External Review, если критически важные материалы не удалось исследовать.

## 5. Проверка требований WHAT

Самостоятельно сопоставь реализацию с GitHub Issue.

Для каждого применимого требования и Acceptance Criterion:

1. Найди соответствующую реализацию.
2. Проверь фактическое поведение.
3. Установи, реализован ли требуемый сценарий.
4. Проверь негативные и пограничные случаи.
5. Найди подтверждающие тесты или другие объективные доказательства.
6. Определи, не нарушены ли согласованные ограничения.
7. Установи итоговый статус.

Используй матрицу:

`Requirement → Acceptance Criterion → Implementation → Test/Evidence → Status`

Статусы:

- `VERIFIED` — требование подтверждено доступными доказательствами.
- `PARTIAL` — реализовано или подтверждено частично.
- `NOT_VERIFIED` — недостаточно доказательств.
- `NOT_IMPLEMENTED` — требуемое поведение отсутствует.
- `OUT_OF_SCOPE` — требование относится к другой утверждённой части задачи.

Не считай Acceptance Criterion выполненным только потому, что coding-agent отметил его в отчёте.

Не требуй от одного частичного PR реализации требований, утверждённо отнесённых к последующим PR.

## 6. Проверка соответствия HOW

Выполни независимую проверку реализации относительно effective Approved Implementation Plan либо требований и критериев Issue на разрешённом `N/A`.

Для каждого применимого шага IMP:

1. Установи предусмотренный технический результат.
2. Найди фактическую реализацию.
3. Сравни алгоритмы и правила обработки.
4. Проверь ответственность компонентов.
5. Проверь предусмотренные взаимодействия.
6. Проверь сохранение контрактов и инвариантов.
7. Установи, выполнены ли обязательные тесты.
8. Выяви отклонения от утверждённого HOW.

Разделяй:

- допустимые локальные детали реализации;
- дефекты реализации утверждённого HOW;
- неутверждённые изменения технического подхода;
- нарушения архитектурных ограничений;
- пропущенные обязательные шаги.

Не считай любое отличие в именовании или организации кода архитектурным отклонением.

Но не принимай замену утверждённого алгоритма или изменение существенного инварианта как допустимую локальную деталь.

## 7. Независимый технический анализ

Проведи собственное исследование качества и корректности реализации.

Не ограничивайся поиском уже известных замечаний Codex/Copilot.

Проверяй применимые аспекты.

### Корректность бизнес-логики

- соответствие доменным правилам;
- правильность алгоритмов;
- жизненный цикл состояний;
- обработку негативных сценариев;
- корректность крайних случаев;
- отсутствие скрытых изменений поведения.

### Архитектура

- ответственность компонентов;
- направление зависимостей;
- соблюдение Domain/Application/Infrastructure/API boundaries;
- повторное использование существующих механизмов;
- отсутствие несогласованного усложнения;
- соответствие ADR/contracts.

### Persistence и конкурентность

Если затронуты соответствующие компоненты, проверь:

- транзакционные границы;
- согласованность данных;
- race conditions;
- CAS;
- идемпотентность;
- порядок блокировок;
- bounded retry;
- монотонность состояний;
- outbox;
- миграции;
- поведение при повторной обработке.

### Безопасность

Проверь применимые:

- authentication/authorization;
- user isolation;
- границы доступа к данным;
- обработку credentials и secrets;
- защиту конфиденциальных данных;
- корректность доверенных источников пользовательской идентичности.

### Контракты и совместимость

- публичные API;
- wire contracts;
- сериализацию;
- nullable behavior;
- обратную совместимость;
- взаимодействие с существующими клиентами;
- обработку некорректных и частичных данных.

### Качество реализации

- обработку ошибок;
- устойчивость к отказам;
- существенные производительные риски;
- достаточность тестирования;
- сопровождение и читаемость;
- соответствие языковой политике;
- отсутствие случайного рефакторинга.

Не проводи формальный аудит несвязанных областей проекта.

Для каждого выявленного дефекта установи конкретную техническую причину.

Не создавай замечания на основании вкусовых предпочтений без технического обоснования.

## 8. Проверка тестирования

Исследуй не только факт существования тестов, но и то, какое поведение они действительно проверяют.

Для обязательных сценариев установи:

1. Есть ли соответствующий тест.

2. Достигает ли он проверяемого пути выполнения.

3. Достаточно ли строгие assertions.

4. Может ли тест выявить предполагаемый дефект.

5. Проверяются ли необходимые негативные и пограничные сценарии.

6. Не замаскированы ли проблемы mocks, fixtures или тестовыми допущениями.

7. Не ослаблены ли ранее существовавшие проверки.


Отдельно оцени необходимость регрессионных тестов для изменённого поведения.

Если тест есть, но не проверяет заявленный инвариант, укажи конкретный пробел.

Если существенная ошибка может существовать при успешном CI, объясни почему существующие тесты её не выявляют.

Не требуй тесты, не имеющие отношения к изменённому поведению.

## 9. Проверка CI

Получай результаты непосредственно из GitHub.

Для каждого обязательного check установи:

- название проверки;

- связанный commit SHA;

- workflow run или check URL;

- итоговое состояние;

- существенные ошибки;

- причины пропуска, если применимо.


Различай:

- `SUCCESS`;

- `FAILED`;

- `PENDING`;

- `SKIPPED`;

- `NOT_AVAILABLE`.


Проверяй, что CI относится именно к текущему head SHA.

Не используй результаты предыдущего HEAD как доказательство корректности нового HEAD.

Не считай пропущенный check успешным. Установи, является ли пропуск предусмотренным и допустимым.

Если CI ещё выполняется, укажи это в заключении.

Успешный CI не заменяет самостоятельный анализ корректности кода.

## 10. Анализ Codex/Copilot

Получи актуальные:

- Codex reviews и comments;

- Copilot reviews и comments;

- inline review threads;

- состояния resolved/unresolved;

- устаревшие комментарии;

- комментарии автора с объяснениями исправлений.


Для каждого существенного замечания:

1. Определи источник.

2. Установи исходный контекст замечания.

3. Проверь актуальность относительно текущего HEAD.

4. Самостоятельно оцени его техническую обоснованность.

5. Подтверди или опровергни дефект.

6. Проверь, устранён ли дефект фактическим кодом.

7. Проверь наличие достаточных тестовых доказательств.

8. Установи состояние соответствующего thread.


Используй классификацию:

- `VALID` — замечание подтверждено.

- `INVALID` — замечание технически необоснованно.

- `OBSOLETE` — замечание относилось к старой реализации и уже неактуально.

- `DUPLICATE` — повтор другого замечания.

- `NEEDS_EVIDENCE` — имеющихся данных недостаточно.


Для VALID findings дополнительно определяй `BLOCKER` или `NON_BLOCKER`.

Не принимай замечания других агентов автоматически.

Не считай разрешённый thread доказательством исправления без проверки кода.

Не считай отсутствие Codex/Copilot review доказательством отсутствия проблем.

Различай отсутствие review, ожидающее review и завершённую проверку без замечаний.

Не публикуй ответы и не разрешай threads.

## 11. Формирование findings

Объедини подтверждённые замечания в единый реестр.

Используй идентификаторы:

`ER-01`, `ER-02`, `ER-03` и далее.

Для каждого finding укажи:

**Идентификация**

- ID;

- название;

- источник;

- статус обоснованности;

- серьёзность, если замечание подтверждено.


**Технические доказательства**

- файл и участок кода;

- permalink на проверяемый commit, если доступен;

- фактическое поведение;

- ожидаемое поведение;

- нарушенное требование, контракт или инвариант;

- воспроизводимый сценарий либо конкретную причинно-следственную цепочку.


**Последствия**

- на что влияет дефект;

- при каких условиях проявляется;

- какие данные или сценарии могут пострадать;

- может ли проблема вызвать регрессию.


**Первопричина**

- техническое объяснение обнаруженного недостатка;

- связь с существующей архитектурой.


**Исправление**

- рекомендуемое направление устранения;

- необходимые регрессионные проверки;

- требуется ли изменение WHAT/HOW или новое Human Decision.


На этапе External Review не составляй полный исполнительский промт coding-agent.

Точное проектирование исправлений выполняется отдельно на этапе №9.

### Критерии серьёзности

`BLOCKER` — подтверждённый дефект или нарушение обязательного workflow, препятствующее безопасному принятию текущей реализации.

`NON_BLOCKER` — подтверждённое замечание, не препятствующее принятию при соблюдении требований и приемлемом риске.

Не создавай дублирующие findings.

Не представляй неподтверждённые предположения как установленные дефекты.

Если доказательств недостаточно, используй `NEEDS_EVIDENCE`.

## 12. Проверка документации

Проверь документацию, относящуюся к изменённому поведению.

Установи:

- отражает ли документация фактическую реализацию;

- не описываются ли ещё не реализованные возможности как завершённые;

- согласованы ли API и contract docs;

- соответствует ли ROADMAP фактическому состоянию;

- соблюдена ли языковая политика.


Не требуй несвязанных изменений документации.

Не изменяй документы самостоятельно.

## 13. Reviewed-state fingerprint

Зафиксируй точное состояние, по которому проводится External Review:

- repository;

- PR number и permalink;

- head branch и полный head SHA;

- целевая ветка, её полный SHA и BASE из метаданных PR, если она отличается;

- связанный Issue;

- Base Approved Plan permalink и Amendment permalinks в порядке комментариев либо `N/A` со ссылкой на разрешение;

- существенные метаданные PR;

- доступные признаки состояния WHAT/HOW;

- применимые запуски и обязательные проверки по общему блоку «Версии и CI»;

- актуальное состояние reviews и review threads.


Этот fingerprint должен позволять однозначно установить, какой именно код и какой effective HOW были проверены.

Не подменяй его датой проверки или номером PR.

Представь проверенное состояние компактным блоком по общему шаблону. Для каждого существенного вывода укажи, что именно подтверждено, на какой версии и каким доказательством. Отдельно перечисли открытые замечания и решения владельца. Если последующая проверка по §14 обнаружила изменение состояния, обнови запись либо обозначь, какие выводы потеряли актуальность. Успешный первичный External Review может служить исходной точкой №12, если обязательных исправлений не осталось.

### Проверенное состояние

- Объект — <репозиторий, PR, Issue>.
- Требования — <проверенный объём WHAT>; <ссылка и версия Approved Plan>; <Amendments по порядку или «нет»>.
- Подтверждено — <критерий или замечание → вывод → доказательство>. Укажи среду, если от неё зависит вывод.
- Открыто и принято владельцем — <замечание → статус → решение, его источник и границы>.
- Версии и CI — <заполненный блок «Версии и CI» из `trade-system-pr-review`>.
- Состояние PR — <Draft, mergeability, существенные метаданные, reviews, threads, approvals>.
- Основание записи — <этап, итог ревью, время последней сверки>; <предыдущий отчёт, если применимо>.

## 14. Повторная проверка актуальности

Перед итоговым заключением повторно получи:

1. Текущий head SHA.

2. SHA вершины целевой ветки и BASE в метаданных PR, если она отличается.

3. Существенное состояние PR metadata.

4. Связанный Issue.

5. Base Approved Plan.

6. Все действующие Amendments.

7. Актуальный CI.

8. Новые reviews и потенциальные blocker findings.


Сравни результат с reviewed-state fingerprint.

Если изменился HEAD, BASE, effective HOW или другие существенные элементы проверяемого состояния, не представляй результаты старого анализа как актуальные.

Повтори необходимую часть проверки либо зафиксируй блокировку до нового review.

Если изменился только статус CI без изменения кода, обнови соответствующее заключение, не объявляя автоматически весь анализ кода недействительным.

Не используй устаревший review для подтверждения Merge Readiness.

## 15. Финальный External Review Report

Представь подробный отчёт.

### 1. Паспорт проверки

Repository, PR, Issue, head/base SHA, время и доступные источники.

### 2. Достоверность WHAT/HOW

Проверка основания: Base Plan, Amendments и effective HOW либо Issue, `N/A` и разрешение владельца.

### 3. Покрытие требований

Матрица `Requirement → AC → Implementation → Evidence → Status`.

### 4. Соответствие Implementation Plan

Результаты проверки шагов IMP и архитектурных ограничений.

### 5. Независимый технический анализ

Выводы по применимым категориям: корректность, архитектура, безопасность, конкурентность, контракты.

### 6. BLOCKER findings

Полный реестр подтверждённых блокирующих замечаний.

### 7. NON_BLOCKER findings

Подтверждённые замечания меньшей серьёзности.

### 8. Codex/Copilot

Статус проверок и классификация замечаний.

### 9. Review threads

Открытые, разрешённые, устаревшие и требующие внимания обсуждения.

### 10. Тестирование и CI

Фактические результаты и недостатки покрытия.

### 11. Документация

Результаты проверки актуальности.

### 12. Reviewed-state fingerprint

Зафиксированное проверенное состояние.

### 13. Итоговое заключение

Первой строкой укажи вердикт External Review и проверенный HEAD. Затем укажи подтверждённые блокирующие замечания и ближайшее действие. Отдельной строкой приведи обязательное поле `Merge readiness = READY / NOT_READY / UNVERIFIED`, момент оценки и решающее основание. Окончательный допуск к решению владельца устанавливается на №12.

### 14. Следующие действия

Что необходимо исправить или дополнительно подтвердить, прежде чем продолжать процесс.

Не повторяй большие фрагменты кода без необходимости.

Предоставляй точные ссылки и технические доказательства.

## 16. Итоговый статус

Используй один статус External Review:

- `REVIEW_PASSED` — технический review завершён, блокирующие дефекты не выявлены, имеющихся доказательств достаточно.

- `CHANGES_REQUIRED` — выявлены подтверждённые проблемы, требующие исправления.

- `REVIEW_BLOCKED` — нарушены обязательные условия доверенного workflow.

- `REVIEW_INCONCLUSIVE` — недостаточно данных для достоверного заключения.


При `REVIEW_PASSED` и отсутствии обязательных исправлений ближайший обычный шаг — №11. При `CHANGES_REQUIRED` укажи замечания для №9. При `REVIEW_BLOCKED` или `REVIEW_INCONCLUSIVE` назови конкретное условие, необходимое для завершения первичного ревью.

Отдельно укажи:

`Merge readiness = READY / NOT_READY / UNVERIFIED`

`READY` допускается только при выполнении всех применимых требований workflow, подтверждённом обязательном CI текущего HEAD, отсутствии блокирующих замечаний и актуальном reviewed-state fingerprint.

Если Draft или другое подтверждённое ограничение GitHub препятствует слиянию, укажи `Merge readiness = NOT_READY` и конкретное препятствие. Технический вердикт при этом может быть `REVIEW_PASSED`. Если известного блокера нет, но обязательное условие не удалось проверить, укажи `UNVERIFIED`. Разрешение владельца и факт слияния фиксируются отдельно.

`REVIEW_PASSED` не означает автоматическую готовность к merge.

Даже если `Merge readiness = READY`, слияние запрещено без отдельного явного Human Merge Gate.

**Coding-agent:**

### Что дальше в ответе

В конце ответа выбери одно ближайшее действие по фактическому результату и учти уже выполненные шаги и явные разрешения. Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. При подтверждённых замечаниях, требующих FIX, дай команду по №9 с их ID. После успешного первичного ревью без обязательных FIX предложи №11. Если вывод ограничен отсутствующим фактом или выполняющейся проверкой, укажи конкретное условие продолжения.

## 18. Ограничения

Работай исключительно в режиме аналитической проверки.

Не изменяй код или тесты.

Не редактируй Issue, Approved Plan, Amendments, ADR или документацию.

Не создавай ветки, commits или Pull Requests.

Не выполняй push.

Не публикуй GitHub review comments.

Не разрешай и не закрывай review threads.

Не подготавливай полный исполнительский промт coding-agent на этом этапе.

Не исправляй findings самостоятельно.

Не выполняй merge.

**После завершения External Review представь полный отчёт и остановись. Следующий этап — отдельный анализ и подготовка Review Fixes, если они требуются.**
