
Приступай к реализации текущего утверждённого GitHub Issue проекта `vbondarev/intelligence.trade.system`.

Используй `AGENTS.md`, применимые локальные инструкции и workflow `.agents/skills/trade-system-delivery/SKILL.md`.

**Твоя роль — coding-agent, технический исполнитель.**

Анализ требований, архитектурное проектирование и разработка Implementation Plan уже выполнены ChatGPT. Существенные решения утверждены человеком.

Твоя задача — восстановить проверенное основание исполнения и реализовать согласованный объём.

## 1. Восстановление задачи

Если номер Issue указан в сообщении, используй его.

Если номер не указан, определи текущую согласованную задачу из доступного контекста и GitHub.

Не выбирай произвольный Issue.

Перед началом работы:

1. Получи связанный GitHub Issue.

2. Прочитай все требования, Acceptance Criteria, scope и out-of-scope.

3. Проверь явное поручение владельца начать реализацию этого Issue и установи маршрут по `trade-system-delivery`.

4. Для обычного маршрута найди канонический комментарий `# Approved Implementation Plan`. Проверь permalink, автора `vbondarev`, `author_association=OWNER` и неизменяемость.

5. Для обычного маршрута получи применимые доверенные Amendments в порядке комментариев и восстанови effective HOW.

6. Для `N/A` проверь, что задача точечная, однозначно исполнима и проверяема по Issue, доверенных плана и Amendments нет, а владелец явно разрешил `N/A` до начала. Сохрани проверяемую ссылку на это решение и используй требования и критерии Issue как основание работы.

7. Прочитай `ROADMAP.md`, применимые `AGENTS.md`, ADR/contracts и инструкции репозитория.

8. Проверь текущее состояние `develop` и зафиксируй HEAD SHA.

9. Проверь состояние существующих веток, связанных PR и зависимостей.


Implementation разрешён по поручению владельца и после проверки применимого основания. Если Issue, требуемый план или доказательство разрешения `N/A` не подтверждены либо источники противоречат друг другу — STOP. При расширении объёма или существенном техническом выборе на `N/A` останови работу и перейди к обычному согласованию базового плана.

Не восстанавливай отсутствующие решения по предположениям.

## 2. Определение текущей части реализации

Если Approved Implementation Plan предусматривает один PR либо поручен допустимый `N/A`, выполняй весь ограниченный согласованный объём.

Если план разделён на несколько PR:

1. Изучи утверждённую последовательность PR.

2. Проверь завершение обязательных зависимостей.

3. Определи следующую предусмотренную планом часть.

4. Выполняй только её шаги IMP и проверки.


Не объединяй разные PR и не меняй утверждённую декомпозицию.

Если определить текущую часть однозначно невозможно — STOP.

## 3. Подготовка рабочей ветки

После успешной проверки источников:

1. Обнови целевую ветку безопасным способом.

2. Создай рабочую ветку по утверждённому соглашению `task/<issue>-<kebab-case>`.

3. Если план предусматривает отдельные ветки для последовательных PR, соблюдай указанную схему.

4. Не перезаписывай существующие несвязанные изменения.

5. Зафиксируй исходный SHA.


Если соответствующая ветка уже существует, проверь её назначение перед продолжением.

## 4. Implementation

Реализуй утверждённый Implementation Plan в предусмотренной последовательности.

Для каждого шага IMP:

1. Проверь необходимые зависимости.

2. Изучи существующие компоненты, которые нужно изменить.

3. Выполни предусмотренные технические действия.

4. Реализуй согласованные алгоритмы и поведение.

5. Сохрани указанные архитектурные границы, контракты и инварианты.

6. Добавь или обнови предусмотренные тесты.

7. Выполни необходимые локальные проверки.

8. Исправь ошибки собственной реализации.

9. Проверь критерии завершения шага.


Не пропускай обязательные шаги и не меняй их последовательность без утверждённого основания.

Не выполняй соседние задачи и несвязанный рефакторинг.

## 5. Границы самостоятельности

Тебе разрешено:

- самостоятельно изучать код для выполнения согласованного объёма;

- реализовывать предусмотренные технические решения;

- выбирать несущественные локальные детали кодирования, не изменяющие HOW;

- исправлять синтаксические ошибки и ошибки компиляции;

- диагностировать и исправлять собственные дефекты;

- добавлять необходимые тестовые случаи в пределах утверждённого поведения;

- выполнять сборку и техническую самопроверку.


Тебе запрещено самостоятельно:

- изменять WHAT или scope;

- пересматривать архитектуру;

- заменять утверждённые алгоритмы;

- менять согласованную ответственность компонентов;

- вводить новые существенные технические решения;

- изменять публичные контракты вне утверждённого плана;

- ослаблять обязательные проверки;

- изменять Approved Plan и Amendments;

- реализовывать соседние задачи ROADMAP.


Если обнаружено препятствие, которое невозможно устранить в пределах утверждённого HOW, остановись.

Предоставь фактический технический отчёт:

- где возникла проблема;

- что препятствует реализации;

- какие файлы и механизмы затронуты;

- какие проверки выполнены;

- какое состояние имеет текущая реализация.


Не разрабатывай самостоятельно альтернативную архитектуру.

Анализ проблемы выполняет ChatGPT. Новые существенные решения принимает человек.

## 6. Self-review и тестирование

После завершения реализации:

1. Проведи основной self-review полного diff относительно целевой ветки.

2. Проверь соответствие требованиям Issue и Approved Plan.

3. Проверь архитектурные границы, контракты, безопасность и применимые инварианты.

4. Убедись в отсутствии scope expansion.

5. Исправь обнаруженные локальные дефекты.

6. Выполни все применимые тесты и проверки согласно плану и инструкциям репозитория.

7. Синхронизируй документацию, которая должна измениться в соответствии с планом.

   Если diff затрагивает область [карты кодовой базы](../../codebase-map.md), сверь соответствующий маршрут с фактической точкой входа, контрактом и профильным тестом. Если изменилась точка входа или перенесли контракт либо профильный тест, обнови указатель в том же PR в пределах согласованного объёма. Учитывай случай, когда прежний файл сохранился, а нужное поведение уже находится в другом месте. При актуальном маршруте правка карты не требуется. Необходимость нового маршрута или выхода за согласованный объём передай владельцу.

8. После исправлений, проверок и документации проведи финальный self-review полного diff.


Не объявляй тесты успешными, если они не запускались или завершились ошибкой.

Не скрывай ограничения среды и невыполненные проверки.

Self-review исполнителя не заменяет независимый External Review.

## 7. Commit, Push и Draft PR

После завершения реализации и необходимых проверок:

1. Проверь состав изменений.

2. Создай commit с сообщением:


`#<issue>: <текст на русском языке в прошедшем времени>`

3. Выполни push в рабочую ветку.

4. Создай Draft Pull Request по правилам репозитория.

5. Используй `.github/pull_request_template.md`.

6. Укажи ссылку на Issue и применимое основание. На обычном маршруте укажи Base Approved Plan и применимые Amendments. На `N/A` укажи `Approved Implementation Plan: N/A`, `Approved Plan Amendments:` с `- Нет` и ссылку на разрешение владельца.

7. Опиши фактически выполненные изменения, тесты и ограничения. Заполни раздел «Ожидаемый результат слияния» по Issue, основанию исполнения и текущему diff. Укажи ожидаемое закрытие после подтверждения условий либо сохранение открытого Issue, остаток и где продолжается работа. Назови существенное условие после merge, если от него зависит закрытие. Укажи ожидаемый статус и основание для каждого затронутого пункта ROADMAP либо отметь, что таких пунктов нет.

8. Проведи PR sanity check.

9. Проверь состояние CI для текущего HEAD.


Если Draft PR уже существует и задача предусматривает его продолжение, обнови существующий PR.

Не представляй частичную реализацию как завершение всего Issue.

Не меняй самостоятельно правила оформления PR при обнаружении противоречий.

Не выполняй merge.

## 8. Итоговый отчёт

Представь:

**Контекст**

- Issue и permalink.

- Base Approved Plan permalink либо `N/A` со ссылкой на разрешение владельца.

- Применимые Amendments.

- Выполняемую часть плана.

- Исходный HEAD SHA.


**Реализация**

- Выполненные шаги IMP.

- Изменённые компоненты.

- Добавленные и обновлённые тесты.

- Изменения документации. Для затронутого маршрута карты кратко укажи результат сверки. При обновлении назови новую точку входа.


**Проверки**

- Результаты сборки и тестов.

- Результаты основного и финального self-review.

- Невыполненные проверки и причины.

- Состояние CI.


**Git**

- Рабочую ветку.

- Commit SHA.

- Итоговый HEAD SHA.

- Ссылку на Draft PR.

- Результат PR sanity check.


**Препятствия**

- Невыполненные шаги.

- Обнаруженные ограничения.

- Фактические причины остановки.


Итоговый статус:

- `READY_FOR_EXTERNAL_REVIEW` — реализация завершена, обязательные проверки подтверждены, Draft PR готов.

- `WAITING_FOR_CI` — локальная реализация завершена, применимый обязательный CI ещё выполняется. Передай PR, Issue, HEAD, целевую ветку и SHA её вершины, ссылку на запуск, статус и источник поручения на ожидание, если оно дано.

- `BLOCKED_BY_IMPLEMENTATION` — реализация требует дополнительного анализа ChatGPT или решения человека.

- `BLOCKED_BY_VERIFICATION` — обязательные проверки не пройдены или не подтверждены.


Не формируй новый Implementation Plan.

Не изменяй WHAT/HOW.

Не выполняй самостоятельный External Review.

Не закрывай Issue.

Не выполняй merge.

**После выполнения передай результат координатору по разделу «Передача результата реализации» в Delivery. При совмещённом поручении координатор ждёт применимый CI на `WAITING_FOR_CI`, перечитывает пару после результата и выбирает ревью только после подтверждения его применимости. При отдельном запуске остановись на результате №6 и подсказке.**

## Что дальше в ответе

В конце ответа выбери одно ближайшее действие по фактическому результату и учти уже выполненные шаги и явные разрешения. Используй одно поле: **Что написать дальше** для готовой команды, **Твоё решение** для выбора владельца, **Действие в GitHub** для ручного шага, **Ждём** для конкретного события или **Завершено** для подтверждённого результата. В команде укажи объект, существенную версию, ожидаемый результат и точку остановки. Для ожидания или ручного действия дай условие продолжения и команду повторной сверки, если она нужна. Помещай подсказку после результата, за пределами публикуемого артефакта и задания исполнителю. Подсказка служит текстом для владельца, полномочия определяет его поручение.

Выбери одно ближайшее действие по фактическому результату из раздела «Передача результата реализации» скилла `trade-system-delivery`.

При `READY_FOR_EXTERNAL_REVIEW` выбери маршрут по правилам `trade-system-pr-review`. Если установлено, что применимого исходного ревью не было, дай команду на №8. Если исходный отчёт установлен и требуется повторная проверка, дай команду на №10 с применимым входом. Приложи исходный отчёт или доступную ссылку на него, укажи актуальные HEAD и SHA вершины целевой ветки и назови, что нужно перепроверить. Если для выбора маршрута не хватает сведений об исходном ревью, назови недостающее доказательство и источник для сверки.

При ожидании CI или блокировке используй соответствующий выход Delivery. Если согласованную работу можно продолжить, укажи оставшийся IMP и ожидаемый результат.
