# Issue #225 — срок заполнения формы Identity

[Утверждённый Amendment о форме входа Identity](https://github.com/vbondarev/intelligence.trade.system/issues/225#issuecomment-6950802243) опубликован и перечитан в Issue #225. Он дополняет [Amendment о продлении действующей BFF-сессии](https://github.com/vbondarev/intelligence.trade.system/issues/225#issuecomment-6949333752). Основание — SC 2.2.1 для входа. Применяются IMP-01–IMP-07, включая обязательный [Windows WebKit gate](https://github.com/vbondarev/intelligence.trade.system/issues/225#issuecomment-6884893121).

## Как работал вход до Amendment

1. BFF начинает OIDC challenge до показа формы Identity. ASP.NET Core по умолчанию задаёт 15 минут для remote authentication и nonce. Браузер получает correlation и nonce cookies. [RemoteAuthenticationOptions](https://raw.githubusercontent.com/dotnet/aspnetcore/v10.0.0/src/Security/Authentication/Core/src/RemoteAuthenticationOptions.cs) · [OpenIdConnectOptions](https://raw.githubusercontent.com/dotnet/aspnetcore/v10.0.0/src/Security/Authentication/OpenIdConnect/src/OpenIdConnectOptions.cs)
2. Razor-форма отправляла пароль отдельным POST на Identity с antiforgery token. После успешного POST Identity продолжал исходный authorization request. При сбое callback BFF возвращал пользователя на публичную страницу.

### Проверка

На отдельном HTTP Compose-стенде с реальными BFF, Identity и API измерены сроки cookies у формы. Chromium — 900 секунд, мобильный WebKit на Windows — 899 секунд. Контрольный вход без ожидания прошёл в обоих браузерах.

- **Chromium — дефект воспроизведён.** После 902 секунд естественного ожидания обе временные cookies исчезли. Форма оставалась видимой с введёнными данными. Identity принял POST (`302`), но BFF при callback вернул пользователя на `/` без предупреждения или объяснения. Browser session не создана, `GET /bff/auth/session/timing` вернул `401`. После отдельного нажатия «Войти» новый OIDC challenge завершился успешно с уже созданной SSO-сессией Identity.
- **Windows mobile WebKit — отказ подтверждён с ускоренным истечением.** Длительный прогон остановился до POST, поскольку API Playwright всё ещё перечислял обе cookies. В отдельном тестовом профиле срок только этих cookies сократили до 8 секунд и проверили HTTP-запрос. После истечения Playwright по-прежнему показывал две cookies, а реальный запрос `/signin-oidc` не передал ни одной. BFF вернул браузер на `/`, проверка сессии дала `401`. Длительная отправка формы в WebKit не проверена. Это наблюдение относится к временным OIDC cookies и не меняет результат отдельного Windows HTTPS gate для BFF session cookie.

Для повторения откройте вход через Web в чистом профиле. Измерьте сроки cookies для пути `/signin-oidc` без записи значений. Сравните немедленную отправку формы с отправкой через 2–3 секунды после истечения обеих cookies. Запишите путь после callback, наличие BFF-сессии и результат повторного входа. В отдельном автоматизированном E2E можно имитировать истечение удалением только временных OIDC cookies. Этот E2E проверяет механизм отказа, а длительный прогон проверяет реальную границу времени.

## Оценка WCAG 2.2.1

**Результат до Amendment — FAIL на маршруте входа Web через BFF.** Таймер OIDC становился пользовательским ограничением, поскольку запускался до заполнения формы. В Chromium после его истечения исходный проход нельзя было завершить тем же действием. W3C включает серверные таймеры в область критерия и допускает essential exception при обоснованной необходимости. Срок начатого OIDC challenge применялся также к вводу credentials. [WCAG 2.2.1](https://www.w3.org/TR/WCAG22/#timing-adjustable) · [Разъяснение W3C](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)

## Утверждённое решение

**Показывать форму Identity до создания OIDC challenge.** Пользователь завершает ввод в обычной защищённой форме Identity. BFF создаёт свежий OIDC challenge при возврате после успешного входа. Нынешний срок correlation и nonce применяется к протокольному обмену после ввода. Подход не требует держать OIDC cookies или пароль дольше.

1. Когда BFF-сессии ещё нет, существующий `GET /bff/auth/login` отправляет браузер на страницу подготовки входа Identity. Сохраняется проверенный локальный путь назначения в Web. Identity использует действующую SSO-сессию либо показывает форму входа. `POST /account/login` проверяет antiforgery token и credentials с прежними правилами блокировки. Его продолжение внутри Identity — локальный путь, созданный сервером. Подготовка входа не создаёт временных OIDC cookies и не устанавливает срок завершения формы.
2. После успешного POST браузер переходит на локальный маршрут продолжения в Identity через `303 See Other`. При действующей SSO-сессии Identity может сразу выполнить продолжение. Переход на явный маршрут BFF выполняется методом GET. Публичный origin BFF выбирается из конфигурации deployment и сверяется с зарегистрированным callback для `trade-web-bff`. Клиент задаёт только локальный путь назначения, который проверяется на обеих границах. Этот переход не передаёт имя, пароль, claims, токены или доказательство авторизации. Сведения о субъекте BFF принимает из стандартного валидированного OIDC-ответа.
3. BFF запускает свежий Authorization Code + PKCE challenge с `prompt=none`. Identity при отсутствии действующей SSO-сессии возвращает штатный `login_required` через OpenIddict. Таким образом, этот краткий протокольный этап не открывает форму с запущенным таймером. При потере SSO или ошибке нового challenge пользователь получает доступное объяснение и действие для повторного входа. Переходы ограничены и не повторяются автоматически по кругу. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)
4. Выдача BFF-сессии по-прежнему требует стандартной проверки callback, включая issuer, state, correlation, nonce и PKCE. Сохраняются текущие правила для уже авторизованного BFF, явного `prompt=login`, OIDC logout, защиты cookie, CSRF и realtime. Ожидание на форме не продлевает BFF-сессию. Для production оба публичных origin используют HTTPS.

Изменение добавляет подготовительный переход через Identity перед началом OIDC. Потребуются контракт продолжения входа и конфигурация доверенного origin BFF в Identity. Увеличение срока исходного challenge сохранило бы зависимость формы от протокольного таймера. Продление до десяти раз потребовало бы ротации OIDC-состояния во время заполнения формы.

**Проверка осуществимости до реализации — 2/2 PASS.** В двух чистых профилях браузер открыл `/account/login`, вошёл в Identity без OIDC cookies, затем инициировал штатный BFF login. Пользователь попал в «Подключения» по локальному пути из `returnUrl` без второй формы. Действующие маршруты после Amendment описаны в [контракте BFF](../web-bff-contract.md).

Область этого решения — интерактивный вход Web-клиента через BFF. Прямые запросы к OIDC Authorization Endpoint сохраняют стандартную семантику, включая принудительный повторный ввод при `prompt=login`. Приёмка должна отдельно указать, какие маршруты пользователя входят в заявляемую область SC 2.2.1.

## Критерии проверки Amendment

1. В Chromium и mobile WebKit открыть форму без SSO, дождаться интервала дольше исходных 15 минут и выполнить один POST. Приложение открывается без повторной отправки формы. До POST у ожидающей формы нет correlation/nonce cookies для этого входа. После POST создаётся один свежий challenge и завершается на штатном callback. Детерминированный тест с управляемыми часами проверяет ту же последовательность без длительного ожидания.
2. Проверить существующую SSO-сессию, явный `prompt=login`, неверные credentials и lockout, истечение SSO между шагами, ручной повтор после сбоя и прямую ссылку на защищённую страницу. В двух вкладках локальные назначения не смешиваются, а подмена внешнего origin, параметров и callback отклоняется. Проверить сохранение пользовательской изоляции в разных браузерных контекстах и смену SSO пользователя между шагами.
3. Проверить antiforgery, неверные state/correlation/nonce/PKCE, повтор устаревшего callback, внешний redirect и отсутствие передачи credentials и токенов новым маршрутом. Проверить действующую BFF-сессию, logout, штатное продление и realtime recovery.
4. На входе и при восстановлении после ошибки проверить фокус, текст и объявление NVDA, ширину 320 CSS px и zoom 400%. Зафиксировать область SC 2.2.1, которую подтвердили этим проходом.
5. Повторить обязательный Windows WebKit HTTPS gate на реальной сессии, без изменения его assertions. При FAIL сохранить блокировку READY_FOR_EXTERNAL_REVIEW и merge.

## Результаты повторной проверки

На пересобранных Identity, BFF и frontend заполнили форму в чистых контекстах Windows Chromium и Windows mobile WebKit (iPhone 13). Через 961 секунду поля сохраняли ввод, запросов `/connect/authorize` и correlation/nonce cookies у формы было 0. В каждом браузере один POST вернул `303`, был создан один challenge `prompt=none` с Authorization Code + PKCE S256, затем `/app` открылся и `GET /bff/auth/session/timing` вернул `200`. Ожидание было реальным, без подмены часов. Срок протокольных cookies не менялся.

Полный browser E2E — **82 PASS, 11 SKIP, 1 FAIL**. Пропуски заданы конфигурацией браузеров. Realtime recovery — **4/4**, E2E нового порядка входа — **14/14**. Подтверждены повтор после потери SSO, прямая ссылка, независимые назначения двух вкладок, явный `prompt=login`, антифорджери и блокировка старого callback, подмены `state`, `nonce` и PKCE. При обновлении формы во второй вкладке Identity переиздаёт antiforgery token для текущего principal. Интеграционная проверка с двумя тестовыми пользователями подтвердила, что свежий challenge использует текущую Identity SSO. Единственный непройденный браузерный тест сообщает `SameSite=None` вместо `Lax` в Windows mobile WebKit.

В Chromium при реальном zoom 400% ширина viewport составила 316 CSS px (1266 при 100%). Форма и экран повтора не требовали горизонтальной прокрутки. После сбоя фокус перешёл на «Начать вход заново». Вход с повтором через Enter прошёл. Проверки axe, фокуса и reflow экрана повтора при 320 CSS px прошли в обоих браузерах.

В установленном Chrome со Speech Viewer наблюдались фактические объявления NVDA для полей «Имя пользователя» и «Пароль», затем «Не удалось завершить вход. Начните вход заново» и «Начать вход заново, кнопка в фокусе». Ошибка воспроизведена удалением Identity SSO после успешного POST и до перехода в BFF на изолированном стенде.

Отдельный Windows HTTPS-прогон — **3 PASS, 1 FAIL**. Серверный заголовок session cookie содержал `Secure`, `HttpOnly` и `SameSite=Lax`. Windows mobile WebKit отправил session cookie в cross-site fetch, где сервер ожидал `session: false` вместе с `control: true`. Контрольная cookie присутствовала. Оба браузера прошли HTTPS-проверку продления и CSRF. Обязательный gate сохраняет статус **FAIL**.

SC 2.2.1 имеет статус **PASS** для обычного интерактивного входа Web через BFF и действующей BFF-сессии в [матрице WCAG](g08-wcag22-aa-matrix.md).
