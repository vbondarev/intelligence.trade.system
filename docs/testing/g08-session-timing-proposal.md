# Issue #225 — решение по сроку сессии для согласования

Решение утверждено владельцем и опубликовано в Issue #225. Канонический текст — [Approved Implementation Plan Amendment](https://github.com/vbondarev/intelligence.trade.system/issues/225#issuecomment-6949333752).

## Предлагаемое поведение

Сохранить существующий скользящий срок BFF-сессии в 8 часов по умолчанию и добавить доступное предупреждение за 2 минуты до истечения. Кнопка «Продлить сессию» одним действием возвращает полный настроенный срок существующей сессии. При отсутствии действия сессия истекает по исходному расписанию. Пользователь может выполнить как минимум 10 последовательных продлений. Предупреждение должно оставлять не менее 20 секунд для ответа в поддерживаемом активном браузере. [WCAG 2.2.1, вариант Extend](https://www.w3.org/TR/WCAG22/#timing-adjustable).

Это решение сохраняет автоматический выход при неактивности. Увеличение срока по умолчанию, отключение таймера и ссылка на исключение essential потребовали бы отдельных оснований. Обычный повторный вход после истечения не выполняет условия Extend.

## Контракт BFF и интерфейс

- Предлагаемый `GET /bff/auth/session/timing` возвращает только серверное время и фактический срок действия существующего ticket с `Cache-Control: no-store`. Чтение не инициирует sliding renewal и OAuth refresh. Проверить подавление renewal до работы cookie handler и тестом доказать отсутствие продления срока и session `Set-Cookie` на этом маршруте.
- Предлагаемый `POST /bff/auth/session/extend` принимает действие только для действующего ticket и с существующей antiforgery-защитой. BFF сам назначает новый срок по серверным часам, обновляет ticket и cookie штатным механизмом. Повторная аутентификация, logout, отзыв или истечение имеют приоритет перед поздним запросом продления. Обновление атомарно относительно удаления ticket и сохраняет более новое поколение OAuth-токенов. Совпадение срока cookie и ticket проверить вместе с конкурентными запросами.
- Оболочка приложения сверяет срок без продления по таймеру и при возвращении на вкладку. Перед показом предупреждения сверяет его с сервером, поскольку обычный запрос или другая вкладка могли продлить session. Ошибка сети не считается продлением. Действие в другой вкладке синхронизирует отображение, сервер остаётся источником срока.
- Предупреждение объявляется NVDA один раз на цикл. Оно доступно с клавиатуры при zoom 400% и 320 CSS px. Фокус попадает на действие при открытии предупреждения и возвращается после закрытия. Ввод в формах не теряется при показе или продлении, скрытые поля credentials не сохраняются в browser storage. По возвращении после сна или истечения показывается уже действительное состояние и предлагается обычный вход.
- OIDC callbacks, PKCE, cookie `HttpOnly`/`Secure`/`SameSite=Lax`, CSRF, Origin-проверка и revoke/logout сохраняют свои требования. Продление действует только на BFF ticket и не отменяет окончание OAuth-токена, отзыв и завершение сессии. Realtime использует действительность ticket и действующие правила reconnect/recovery. Оставшийся в открытой вкладке сокет или периодическая проверка срока не заменяют явное продление.

## Приёмка

1. С управляемыми серверными часами проверить предупреждение, окно ответа и не менее 10 циклов продления. Отдельно проверить истечение без действия, без продления при чтении, несинхронные часы, две вкладки, восстановление после сна и временную потерю сети.
2. Проверить реальный BFF/Identity login, серверный ticket и cookie до и после продления, отказ при отсутствии CSRF, после logout, отзыва и истечения, а также гонки продления с logout и token refresh. Никаких токенов или ключа сессии в JSON и JavaScript.
3. Пройти предупреждение в Chromium и mobile WebKit, с клавиатуры, при 320 CSS px, browser zoom 400% и с NVDA. Записать реальную фразу, управление фокусом и сохранение формы при успешном продлении.
4. В изолированном стеке проверить realtime при продлении и истечении, включая прекращение доставки после завершения сессии и recovery из актуального GET после повторного входа. Проверить все оставшиеся пользовательские таймеры на маршруте, включая ожидающие экраны Identity/OIDC. Сбои протокола и повторный вход описать отдельно от бездействия.
5. Сохранить все IMP-01–IMP-07 и их критерии. Обязательный Windows WebKit security gate повторяется с реальной cookie и остаётся блокирующим при FAIL. Прохождение сценариев продления не меняет статус gate.
