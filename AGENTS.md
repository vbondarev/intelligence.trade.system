# Руководство для агента: dotnet-skills

ВАЖНО:
Для любых задач по .NET сначала опирайся на skills и структуру текущего репозитория, а не только на общие знания модели.

Рабочий процесс:
1. Сначала быстро изучи паттерны и соглашения этого репозитория.
2. Затем подбери и вызови подходящие dotnet-skills по имени.
3. Вноси минимально необходимые изменения без лишнего рефакторинга.
4. Явно отмечай архитектурные конфликты, спорные места и риски побочных эффектов.

Общие правила для этого проекта:
- Проект является backend-решением на .NET / ASP.NET Core.
- Предпочитай production-ready решения без демонстрационного кода, если не сказано иначе.
- Сохраняй обратную совместимость API, DTO, контрактов сообщений и схем сериализации, если задача явно не требует breaking changes.
- Учитывай существующую архитектуру, DI-регистрации, жизненные циклы сервисов, конфигурацию и стиль логирования.
- Для изменений в data access учитывай EF Core, SQL-производительность, индексы, N+1, транзакции и конкурентный доступ.
- Для интеграционных сценариев учитывай внешние зависимости, брокеры сообщений, PostgreSQL, контейнеры и тестовую инфраструктуру.
- Для асинхронного и многопоточного кода отдельно проверяй race conditions, deadlocks, cancellation, backpressure и корректность async/await.
- Не предлагай крупный рефакторинг, если задачу можно решить локальным и безопасным изменением.
- Если меняется публичный контракт, миграция данных, схема БД или поведение межсервисного взаимодействия — предупреди об этом явно.

Дополнительные правила именно для этого проекта:
- Для ASP.NET Core endpoint'ов сохраняй понятные контракты запросов/ответов, корректные коды ответа и предсказуемую валидацию.
- Для EF Core запросов сначала оцени форму SQL, количество запросов, необходимость Include / projection / pagination и влияние на PostgreSQL.
- Для PostgreSQL учитывай индексы, блокировки, планы выполнения, стоимость сортировок и фильтрации.
- Для RabbitMQ и межсервисных сообщений не ломай существующие message contracts, routing keys, retry / idempotency поведение без явного указания.
- Для фоновых задач и обработчиков сообщений проверяй устойчивость к повторной доставке, отмене, таймаутам и частичным сбоям.
- Для тестов предпочитай интеграционные тесты на Testcontainers там, где важно проверить БД, брокер или реальную инфраструктуру.
- Для изменений в производительности сначала предложи способ измерения, потом оптимизацию.
- Для изменений в конкурентном коде сначала объясни инварианты и потенциальные гонки, потом предлагай исправление.

Формат ответа агента:
1. Кратко опиши, какие skills выбраны и почему.
2. Покажи минимальный безопасный план изменений.
3. Выполни изменение.
4. Перечисли риски, что проверить после изменения, и какие тесты запустить.
