# Следующий шаг разработки

Ответь на вопрос владельца «Что сейчас нужно сделать по этой задаче и почему?». Выбери одно ближайшее действие для запрошенного объекта. Это может быть запуск промта, решение владельца, исполнение уже утверждённого FIX, ожидание конкретного CI или проверка результата слияния.

Вызов `next-stage` разрешает читать доступные источники и подготовить ответ в чате. Заверши работу после рекомендации или текста задания. Исполнение этапа, запуск тестов и CI, изменение файлов и публикация в GitHub требуют отдельного поручения. Снятие Draft и merge — действия владельца. Разрешение из истории учитывай при выборе действия и его исполнителя.

## 1. Вызов

| Запрос | Что определить |
|---|---|
| `$next-stage #234` | Тип объекта через GitHub и ближайшее действие по нему. |
| `$next-stage PR #233` | Следующий шаг для указанного PR и его проверяемой версии. |
| `$next-stage Issue #225` | Следующий шаг для всей задачи с учётом критериев, связанных PR и зависимостей. |
| `$next-stage по текущей задаче` или `$next-stage` | Активную задачу и текущее действие по контексту чата. Работает до создания Issue. |
| `$next-stage <ссылка на GitHub>` | Репозиторий и объект из ссылки. |
| `$next-stage PR #155 на 26 сентября 2026 года, 00:59:40 МСК` | Состояние и доступные решения на указанный момент. |
| `$next-stage #232 — подготовь задание` | Рекомендацию и короткое задание на выбранное действие. |
| `Подготовь задание на этот шаг` | Задание по предыдущему выводу после сверки его оснований. |

Для номера без ссылки используй `vbondarev/intelligence.trade.system`. Если явно указанный тип расходится с GitHub, обозначь расхождение. Для ссылки на другой репозиторий установи применимость правил AI Project.

По умолчанию оценивай текущее состояние. При историческом запросе используй сведения и решения, существовавшие к указанному моменту. Датированное позднейшее событие можно привести отдельно, если оно показывает, когда вывод утратил актуальность. Учитывай, что сегодняшнее тело Issue или PR могло быть отредактировано после рассматриваемой даты.

## 2. Определи объект и границы задачи

**Для PR** установи его объём, HEAD, целевую ветку, BASE и последнее подтверждённое событие. Родительское Issue нужно для установления WHAT, действующего HOW, исключений и зависимостей. После merge найди результат №14 для конкретного слияния. Если постпроверка завершена, сообщи её фактический итог и остаток, даже если родительская задача продолжается.

**Для Issue** восстанови критерии всей задачи, предусмотренные части плана и связанные PR. Установи, что уже доставлено, какая часть активна и что определяет дальнейшее продвижение. Если постпроверка предыдущего PR является условием следующей части, укажи её первой. Если работа может идти независимо, выбери действие по ближайшей части плана. Запрашивай приоритет только тогда, когда несколько независимых вариантов действительно допустимы и выбор не установлен.

**Для текущей задачи** найди последний содержательный обмен: цель владельца, результат работы и последующее решение. До создания Issue достаточно рабочего названия, Discovery Report, открытого вопроса или черновика WHAT. Упоминание другого PR в примере или зависимости само по себе не меняет текущую задачу. Если два толкования дают разные следующие действия, задай один вопрос с конкретными вариантами.

Если владелец явно спросил и про PR, и про Issue, покажи два подписанных действия. Для каждого используй его собственное условие завершения.

## 3. Собери достаточные доказательства

1. **Карта процесса.** Обзор `docs/development/README.md` задаёт общий маршрут. Промты находятся в `docs/development/prompts/`. Точное имя, вход и полномочия этапа сверяй с выбранным промтом.
2. **Проектные правила.** Используй корневой и применимые по путям `AGENTS.md`, а также workflow нужной стадии: `trade-system-discovery`, `trade-system-delivery` или `trade-system-pr-review`. Установи версию, относящуюся к работе. В AI Project несколько рабочих копий.
3. **WHAT и HOW.** Issue определяет требования. Для реализации и ревью проверь доверенный базовый Approved Implementation Plan и все применимые Amendments в порядке публикации. Для разрешённого `N/A` проверь точечные требования Issue, отсутствие доверенных плана и Amendments, а также источник явного разрешения владельца по `trade-system-delivery`. Более поздняя поправка заменяет только явно указанные положения.
4. **Факты исполнения.** SHA, публикацию плана, коммиты, CI, Draft, состояние Issue и merge подтверждай по GitHub. Для статуса этапа ROADMAP используй документ и аудит в соответствующей версии целевой ветки.
5. **Ревью и решения.** Охват технической проверки устанавливай по самому отчёту. Разрешение владельца — по сообщению или согласованному артефакту с понятным предметом и границами. Сначала используй текущий чат, затем подходящие доступные чаты AI Project, если нужен конкретный недостающий факт. Название чата или его краткое резюме помогает найти первоисточник.

Различай события: подготовлена редакция, содержание утверждено, публикация разрешена, публикация проверена, реализация или возобновление поручены, работа выполнена, результат независимо проверен. Одно сообщение владельца может подтвердить несколько событий. Текст шаблона «Утверждаю…» в файле сам по себе не подтверждает решения владельца.

Собери минимум сведений, достаточный для выбора ближайшего действия. Если уже установлено, что нужен №12, оставь финальную проверку допуска исполнителю №12. Если доказательств не хватает, укажи конкретную неопределённость и действие, которое её разрешит.

## 4. Выбери ближайшее действие

Начни с последнего подтверждённого результата. Для уже начатого этапа проверь, какая работа выполнена и что произошло после неё.

| Состояние | Рекомендация |
|---|---|
| Входные условия выполнены, этап ещё предстоит начать | Назови промт и проверяемый результат. |
| Редакция или FIX готовы и ожидают решения | Назови конкретный предмет утверждения. |
| Содержание согласовано, разрешение на исполнение ещё требуется | Укажи, какое действие предстоит разрешить. |
| Исполнение уже разрешено | Назови исполнителя и действие. |
| Результат опубликован и ожидает проверки | Назови артефакт, версию и требуемую проверку. |
| Единственным препятствием остаётся внешний результат | Укажи конкретный запуск CI, событие или зависимость и условие продолжения. |
| Работа в запрошенных границах завершена, отложена или отменена | Сообщи результат и его область действия. |

### Подготовка задачи — №1–5.4

| Что установлено | Следующий шаг |
|---|---|
| Нужен анализ задачи | **№1 — Discovery.** Для вопроса об актуальности, наличии проблемы или достаточности доказательств выбери целевую проверку. Когда прямой ответ получен, запрос может завершиться. Для подготовки новой задачи к согласованию WHAT выбери полный Discovery. |
| Без выбора владельца нельзя согласовать WHAT, scope или критерий приёмки | **№2 — Human Decisions.** Используй открытый `D-XX` и сравнение из №1. Повторное исследование требуется при новом варианте, изменении основания, конфликте или пробеле. Параметр, явно оставленный для HOW, передай в №4, если он не препятствует согласованию WHAT. |
| WHAT согласован и требуется оформить Issue | **№3 — GitHub Issue = WHAT.** Допустимы единая редакция Discovery либо доступные исходный отчёт, итоговые изменения и реестр решений. При отсутствии открытых решений достаточно результата №1 и команды владельца на подготовку Issue. |
| Готова точная редакция Issue | Если требуется решение владельца, назови его. Если публикация разрешена — **№3.1, Публикация Issue**. После создания проверь опубликованную редакцию. |
| `ISSUE_PUBLISHED_VERIFIED`, `N/A` применим и явно разрешён владельцем | Предложи **№6** с номером Issue и доказательством разрешения. Проверь отдельное поручение начать реализацию. Если его ещё нет, покажи готовую команду для владельца. |
| `ISSUE_PUBLISHED_VERIFIED`, Issue подходит для `N/A`, решения ещё нет | Спроси, разрешает ли владелец `N/A` для этого Issue или выбирает обычный маршрут с №4. |
| `ISSUE_PUBLISHED_VERIFIED`, обычный маршрут с планом | **№4 — Implementation Plan = HOW**, если план предстоит подготовить. Если он уже существует, выбери первое оставшееся действие с учётом редакции, утверждения, публикации и поручений. Сохрани permalink доверенного опубликованного плана. |
| Полная редакция плана подготовлена и ожидает проверки | **№5.1 — Human Plan Review.** Проверь покрытие обязательных критериев, исполнимость и зависимости. Для исторических планов допустимы однозначные связи между разделами. Общая фраза «проверить все AC» не доказывает покрытия конкретного критерия. |
| Требуется изменить HOW до утверждения | **№5.2 — корректировка плана.** После подготовки и проверки полной новой редакции с `READY_FOR_HUMAN_GATE` выбери №5.3. Отдельный повтор №5.1 нужен при конкретном непроверенном основании или по просьбе владельца. |
| Проверенная полная редакция имеет `READY_FOR_HUMAN_GATE` | **№5.3 — утверждение владельцем.** Установи объект и версию. Если владелец уже утвердил эту редакцию, учти принятое решение. |
| План утверждён | Если разрешение на публикацию ещё требуется, предложи владельцу команду для **№5.4**. При явном разрешении ближайшее действие — **№5.4, публикация и проверка**. Для уже опубликованного плана проверь результат публикации. Изменение канонического HOW проходит через Amendment. |

Для `ISSUE_PUBLISHED_VERIFIED` сначала установи состояние плана и поправок по `trade-system-delivery`. При недостатке доказательств укажи источник для сверки. Различай предложенную проверку и её фактический результат.

### Реализация и STOP — №6–7.5

| Что установлено | Следующий шаг |
|---|---|
| Действующий HOW опубликован и проверен или подтверждён разрешённый `N/A` | **№6 — Coding-agent Implementation.** Назови конкретный IMP или часть PR. Для начатой реализации укажи оставшееся действие. Обычная ошибка в пределах согласованного плана исправляется на текущем этапе. |
| Конкретное препятствие мешает продолжить действие, и ещё требуется установить причину или допустимый способ продолжения | **№7.1 — STOP Analysis.** Передай два поля: **Прерванное действие** — этап, объект и конкретная работа, продолжению которой мешает препятствие. **Источник препятствия** — наблюдаемый факт и свидетельство, по которому его можно проверить: отчёт исполнителя, замечание ревьюера, результат CI, сравнение версий или конкретные положения документов. Укажи ссылку, проверенные версии или время, когда от них зависит вывод. |
| После STOP задача больше не подходит для `N/A` из-за расширения объёма или существенного технического выбора, доверенного базового плана нет | Если решение владельца ещё требуется, укажи предмет выбора по №7.1. Если решение принято, сверь опубликованный WHAT с ним. При расхождении сначала предложи согласовать или проверить разрешённое обновление существующего Issue. Когда WHAT подтверждён, выбери №4 для подготовки первого базового плана либо первое оставшееся действие по уже подготовленной редакции. Возобновление реализации требует проверенной публикации утверждённого плана и явного поручения владельца. |
| Решение владельца меняет WHAT или HOW при действующем доверенном базовом плане | №7.2 — подготовить точные изменения. №7.3 — утвердить их редакцию. №7.4 — опубликовать разрешённые изменения и проверить результат. Выбери первое оставшееся действие. |
| Локальное препятствие устранено и результат подтверждён | Продолжи первое оставшееся действие в пределах действующего основания и поручения. Для остановленной реализации — **№7.5** с конкретным IMP. Для FIX, ревью или допуска — действие на прерванном этапе. |
| После поправки нужно продолжать работу | Примени правило возврата из §5. **№7.5 — Resume Implementation** применяется при возобновлении остановленной реализации. |

Для №7.1 различай обнаружение препятствия и решение о формальной остановке работы. Если известно только, что проверка выявила препятствие, укажи затронутое действие и результат проверки. Утверждение «исполнитель остановил работу» требует отдельного подтверждения.

Смена HEAD или BASE сама по себе обрабатывается по §6. Выбирай №7.1, когда обнаружено конкретное препятствие и ещё требуется выяснить, как продолжить работу в рамках действующих WHAT/HOW. Если способ устранения уже установлен, укажи ближайшее оставшееся действие.

| Что установлено | Следующий шаг |
|---|---|
| Реализация готова и установлено, что применимого первичного независимого ревью не было | **№8 — External Review** текущего PR. Укажи HEAD, BASE и существенные исходные замечания. |
| Подтверждены замечания, требующие исправления | **№9 — Review Fixes.** Режим А — спроектировать FIX. Режим Б — оформить задание по уже согласованным FIX. Если задание готово, укажи его редакцию, состояние разрешения и ближайшее действие. |
| Есть исходное независимое ревью и опубликованные FIX | **№10 — Independent Re-review, вход А.** Укажи исходные findings, исправленную версию и требуемую независимую проверку. |
| Есть исходное независимое ревью и существенно изменилось проверенное состояние | **№10, вход Б.** Назови событие и затронутые выводы. Смена BASE при прежнем HEAD может быть достаточным основанием. Для документального изменения после №11 сначала определи маршрут по §6. |
| Первичное или повторное техническое ревью пройдено, обязательных исправлений не осталось | **№11 — Pre-Merge Documentation & Completion.** На маршруте без обязательных FIX допустим результат №8. В команде укажи исходный отчёт по формату «Передача результата» из `trade-system-pr-review`. Если документальные правки уже определены, различай их утверждение, исполнение и проверку. |
| Документация готова и требуется финальный допуск | **№12 — проверка готовности к Human Merge Gate.** Примени правила актуальности из §6. В команде укажи карточку №11 и исходный отчёт. Если обязательный CI — единственное выявленное препятствие помимо Draft, предложи команду на ожидание этого запуска и ручного снятия Draft с финальной сверкой в том же проходе №12. Если Draft уже единственное препятствие, укажи владельцу действие **Ready for review** и условие финальной сверки по №12. |
| №12 выдал актуальный положительный допуск | **№13 — Human Merge Gate.** Укажи PR и проверенное состояние. Если явное решение владельца уже дано и сохраняет силу, назови оставшееся ручное действие. |
| PR слит | **№14 — Post-Merge Verification.** Для запроса по PR установи результат проверки фактического merge в целевую ветку. Отдельно установи допуск №12 для слитой версии и решение владельца №13. Если источник одного из них отсутствует, передай этот пробел в №14. Этапы №12 и №13 задним числом не запускаются. Для запроса по родительской Issue определи её фактическое состояние и оставшееся действие. Если завершённый Issue остаётся открытым, предложи №14 с явным поручением на закрытие по его условиям. |

Основной файл №9 — `Промт №9 — Review Fixes.md`. Выбирай режим по состоянию каждого FIX. Если все обязательные FIX опубликованы и ожидают независимой проверки, следующий этап — №10. Согласованные неблокирующие отсрочки показывай отдельно.

## 5. После Amendment вернись к прерванному действию

Установи:

1. Какое действие ожидало решения: реализация, проектирование или исполнение FIX, независимая проверка, документальная правка либо проверка допуска.
2. Какое препятствие снято и какие положения плана изменены.
3. Что теперь допустимо по WHAT/HOW, какая конкретная редакция утверждена и какие действия владелец разрешил выполнить.
4. Что уже произошло после решения: публикация, исправление, проверка нового состояния.

Если обязательная публикация частичная, укажи недостающий артефакт и действие по №7.4. Перед повторной публикацией требуется сверка GitHub на дубликаты. После подтверждения артефактов выбери первый оставшийся шаг.

- Остановленная реализация — №7.5.
- Прерванное проектирование исправления — №9, режим А.
- Готовый FIX — установить разрешение и перейти к его исполнению.
- Опубликованный FIX — независимая проверка по №10, вход А.
- Решение владельца принимает существующее состояние — проверить его по обновлённому HOW на соответствующем этапе.
- Документальная правка — продолжить согласование, исполнение или проверку в рамках того этапа, где она возникла. Если опубликованный Amendment существенно изменил выводы прежнего независимого ревью, следующий шаг — №10, вход Б.

## 6. Различай №8, №10 и №12 по доказательствам

### Основание независимого ревью

Для повторной проверки установи PR, роль проверяющего, фактический охват предыдущего применимого ревью, его технический вывод и проверенные HEAD/BASE. Допустим отчёт, который владелец явно принял как первичный External Review. Его роль подтверждается решением владельца, а достаточность — содержанием и доказательствами самого отчёта.

Формальный GitHub-статус `APPROVED` не обязателен для существования такого отчёта. Отзыв бота, отсутствие новых findings и зелёный CI по отдельности не подтверждают прохождение проектного независимого ревью.

| Доказательства | Что рекомендовать |
|---|---|
| Установлено, что исходного ревью не было | №8 для актуального состояния. |
| Отчёт мог существовать, но его охват или версию установить не удалось | Проверь доступные ссылки и подходящий чат. Если основание остаётся неизвестным, укажи, чего не хватает. На №12 это `UNVERIFIED`. Полный №8 может создать новое исходное ревью. |
| Установлено прежнее ревью, а его вывод устарел после существенного изменения | На №12 это `STALE_REVIEW`, пока нужная проверка не завершена. После FIX — №10, вход А. После изменения BASE или другого существенного условия без FIX — №10, вход Б. |
| После №11 изменились документы | Определи смысл правки по правилам ниже. Для допустимого документального уточнения при прежней BASE независимая проверка выполняется внутри №12 §4B. |
| Состояние совпадает с проверенным | Укажи оставшийся шаг по документации, финальному допуску или решению владельца. |

### Документальное уточнение, ошибка в тексте или изменение HOW

Сравни прежнее и новое утверждение. Для выбора этапа достаточно установить, от какого пункта Issue, Approved Plan или Amendment зависит вывод, и какое свидетельство реализации с ним связано. Подробную проверку передай исполнителю выбранного этапа.

Проверь, меняет ли новая формулировка хотя бы один ответ: когда функция доступна, что обязан сделать исполнитель, что получает пользователь, какое исключение допускается, при каком результате критерий считается выполненным. Документ может впервые явно назвать зависимость, которая уже закреплена планом. Одного совпадения текста с текущим кодом недостаточно для вывода о соответствии HOW.

| Что установлено | Ближайшее действие |
|---|---|
| Новая формулировка следует из конкретного положения действующих WHAT/HOW, соответствует проверенной реализации и сохраняет обязательства и критерии приёмки | **№12 §4B**, при прежней BASE и только документальной дельте после №11. Укажи изменённое утверждение, его основание и предмет независимой проверки на текущих HEAD/BASE. |
| Документ расходится с однозначным WHAT/HOW. Действующие требования сохраняются, реализация им соответствует, требуется исправить только текст | **№11** с конкретной документальной правкой. Если расхождение установлено на №12, его результат — `NOT_READY`. После исправления заново определи объём проверки по №12 §4. |
| Предлагается ввести или снять обязательное поведение, зависимость, исключение либо критерий приёмки | Назови исходное обязательство и последствия для приёмки. Если требуется выбор владельца — **№7.1** по прерванному действию. Если выбор сделан, примени правило STOP из §4. Для задачи, которая больше не подходит для `N/A`, выбери ближайшее действие по подготовке первого базового плана. При действующем доверенном базовом плане выбери первое оставшееся действие по №7.2–7.4. На №12 подтверждённое расхождение с действующими требованиями даёт `NOT_READY`. |
| Соответствующий Amendment уже опубликован | Проверь его применимость и вернись к прерванному действию по §5. Если поправка существенно меняет выводы прежнего ревью, выбери **№10, вход Б**. |
| Недоступен источник, необходимый для определения смысла правки | Назови недостающий пункт, редакцию или результат проверки. На №12 это `UNVERIFIED`, если классифицировать изменение невозможно. Если существенное изменение ранее проверенного состояния уже доказано, до требуемой перепроверки действует `STALE_REVIEW`. |

Расширение `.md` само по себе не определяет маршрут. Изменение обязательного skill, технического контракта или архитектурного правила может влиять на поведение и требовать №10. Для §4B учитывай как дельту с момента ревью, так и полный текущий diff PR относительно BASE.

### Версии и CI

Если ближайшее действие зависит от актуальности ревью или CI, используй блок «Версии и CI» из `trade-system-pr-review`. Сопоставь текущий HEAD и вершину целевой ветки с BASE события и фактически проверенным кандидатом. Учитывай изменения полного diff, WHAT/HOW, метаданных, reviews, threads и условий владельца. Если расхождение версий влияет на выбор действия, назови его и укажи недостающее доказательство. Отдельно учти ограничения GitHub, которые остаются при зелёном CI. Если PR имеет `BEHIND` и GitHub требует актуальной ветки перед слиянием, предложи синхронизировать ветку PR даже при подтверждённом кандидате текущей пары.

Если сдвинулась только база, отдельный FIX или новый коммит исполнителя не требуется для входа Б. Старый успешный CI сам по себе не подтверждает интеграцию с новой базой.

Для текущего запроса повторно получи HEAD и BASE перед ответом, если их изменение могло бы поменять рекомендацию. Если пара изменилась во время анализа, обнови вывод. При подготовке задания на №10 или №12 укажи, что исполнителю также требуется финальная сверка пары перед вердиктом. Если при сверке обнаружен состоявшийся merge, передай в №14 время слияния, последнюю проверенную пару и сведения о том, был ли положительный итог №12 зафиксирован до merge. Для исторического запроса сохраняй заданную временную границу.

## 7. Различай технический вывод, допуск и действие владельца

№8 и №10 дают технический вердикт и указывают требуемое проектом состояние `Merge readiness` на момент проверки. №12 выносит итог допуска. №13 фиксирует решение владельца. №14 сверяет фактический результат слияния.

Если `REVIEW_PASSED`, но Draft препятствует merge, покажи оба факта. Если владелец велел сохранить Draft, ближайшее действие — дождаться его решения. Когда владелец снял Draft, ближайший шаг — финальная сверка №12 по HEAD, BASE, HOW, CI, approvals и mergeability. Если действующий проход №12 ждёт ручного действия, он продолжит сверку в том же проходе при неизменной паре. При смене пары он завершит проход без допуска, покажет обе пары и фактический статус Draft и определит перепроверку по §6. После положительного допуска учти уже данное Human Merge Decision в пределах его действия.

### Если PR уже слит

Для маршрута по PR найди имеющийся результат №14. Если проверка предстоит или выполнена частично, передай исполнителю три отдельных вопроса.

| Событие | Что установить |
|---|---|
| **Допуск №12 до merge** | Был ли до слияния зафиксирован `READY_FOR_HUMAN_MERGE_GATE` для слитого состояния. Укажи PR, проверенные HEAD/BASE, существенные условия и источник. Если известен только отчёт для прежней пары, назови её и последующее изменение. |
| **Решение №13 до merge** | Какое явное действие разрешил владелец, для какого PR, целевой ветки и при каких условиях. Учитывай источник, позволяющий установить границы решения. Поручение подготовить документацию к закрытию подтверждает полномочия на эту подготовку. |
| **Фактический merge** | По GitHub установи PR, целевую ветку, время, результирующий SHA и соответствие слитого содержимого с учётом способа слияния. |

Для №12 и №13 по отдельности используй формулировки **«подтверждено для слитого состояния»**, **«не подтверждено доступными источниками»** или **«установлено расхождение»**. Приведи источник и время, если оно установлено. При пробеле назови конкретно, чего не хватает. Для вывода о нарушении требуется доказательство, например разрешение только для определённого HEAD и фактически слитое изменение за его пределами.

После merge №14 продолжает проверку содержимого целевой ветки, ROADMAP, Issue и post-merge CI независимо от доступности допуска. Позднейшую проверку датируй временем её проведения. Событие `merged`, результат CI и решение владельца подтверждают каждый свой факт.

Если фактический результат слияния проверен и единственный остаток — неподтверждённый обязательный допуск №12 или решение №13, применим итог №14 `POST_MERGE_UNVERIFIED`. Если установлено нарушение условий допуска, границ решения владельца либо отдельное существенное расхождение обязательных проверок, применим `POST_MERGE_DISCREPANCY`. Пробелы в доказательствах сохраняй отдельными пунктами. Для продолжающегося CI, административного действия и полностью подтверждённого результата используй соответствующий статус из №14. Итоговую постпроверку выполняет исполнитель №14.

### Карточка готовности и завершение задачи

Для №11–14 используй одну карточку. До merge она описывает ожидаемый результат, после merge — его сверку с фактом.

- **PR** — проверенные HEAD/BASE, технический результат, допуск и решение владельца либо фактический merge и итог №14.
- **Issue** — состояние в GitHub, покрытие обязательных критериев, ожидаемое и фактическое действие по закрытию. При частичном выполнении назови остаток.
- **ROADMAP** — для каждого затронутого пункта укажи идентификатор и раздел, ожидаемый статус, фактическую строку в проверяемой версии, связанную сводку и основание. Родительский этап оцени отдельно. До merge используй проверенный HEAD с учётом BASE. После merge используй результирующий SHA и, если он отличается, текущий HEAD целевой ветки.
- **Ближайшее действие** — одно действие по запрошенному объекту.

Если полностью выполненный пункт останется «в работе» после merge, ближайший шаг до слияния — исправление конкретной строки и связанных сводок по №11, затем обновление допуска №12. Если расхождение обнаружено на результирующем SHA, ближайший этап — №14 с фиксацией `POST_MERGE_DISCREPANCY` и точного исправления.

Если критерий по утверждённым правилам проверяется только после merge, укажи событие, ответственного за последующее действие и условие обновления статуса. Пока необходимая проверка или обновление ожидается, сообщи остаток.

Для запроса по PR сообщай результат именно этого PR. Для запроса по всей задаче используй «Завершено», когда подтверждены доставка всего обязательного объёма, ожидаемое состояние Issue и корректные статусы соответствующих пунктов ROADMAP. Завершение дочерней задачи совместимо с продолжающимся родительским этапом.

## 8. Режим «подготовь задание»

Включай по просьбе владельца. Сначала определи ближайший шаг и сверь его актуальность. Проверь, есть ли готовое задание от №9, №11 или другого этапа. Если его цель, редакция и полномочия подходят, используй существующий текст. Если получатель не имеет к нему доступа, передай точную редакцию или доступную ссылку.

Для нового задания выбери нужные правила репозитория и этапа. При различии формулировок сравни обязательные действия и доказательства. Если обе инструкции выполнимы в одном этапе, укажи его точный объём. Если применимые требования требуют другого этапа, исправь рекомендацию. При необходимости нового решения владельца сформулируй предмет выбора.

Подготовь четыре строки.

**Этап и объект** — роль, этап, Issue/PR и проверяемая версия.\
**Сделай** — конкретное поручение, существенная граница или исключение.\
**Основания** — применимые инструкции на нужной версии, WHAT/HOW, поправки и исходный результат.\
**Результат и остановка** — что предъявить, какие действия разрешены и где заканчивается поручение.

Для задания на №7.1 помести «Прерванное действие» в строку **Сделай**, а «Источник препятствия» — в строку **Основания**. В строке **Результат и остановка** запроси классификацию препятствия, ближайшее действие и условие возврата к прерванной работе.

После полного задания дай отдельную короткую команду для этого чата. Подставь выбранный этап, действие и точку остановки. Например, если выбран №3, напиши «Выполни подготовленное выше задание по №3. Покажи черновик Issue здесь». При передаче в другой чат используй полный текст задания.

Если ближайший шаг — одно решение владельца или ожидание CI, назови вопрос либо запуск и условие продолжения. В таком случае отдельное исполнительское задание избыточно.

## 9. Формат ответа

Отвечай по-русски. Начинай с ближайшего действия. Обычно достаточно короткой карточки.

**Следующий шаг — <конкретное действие>.**\
**Объект** — <рабочее название, Issue или PR, существенные версия и момент>.\
**Основание** — <последний подтверждённый результат и почему он ведёт к выбранному шагу>. <Источник>.\
**Промт** — <точное имя файла, только если требуется запуск>.

При обычной рекомендации №7.1 назови прерванное действие в строке **Следующий шаг**, а источник препятствия — в строке **Основание**. Этого достаточно для передачи в промт без отдельного исполнительского задания.

Сверь ближайшее действие с фактическим состоянием задачи и явными разрешениями владельца. В конце ответа используй одно подходящее поле.

- **Что написать дальше** — готовая команда для текущего чата. Укажи действие, Issue или PR при наличии, существенную редакцию или HEAD/BASE, ожидаемый результат и точку остановки.
- **Твоё решение** — конкретный вопрос владельцу или фраза для отправки при согласии с указанной редакцией. Учитывай отдельно утверждение, разрешение на публикацию и поручение на исполнение.
- **Действие в GitHub** — какой объект открыть, что сделать вручную и, если нужна повторная проверка, с какой командой вернуться.
- **Ждём** — конкретный запуск, событие или зависимость, условие продолжения и команда для повторной проверки, если она нужна.
- **Завершено** — подтверждённый результат в границах объекта запроса. Этого поля достаточно для завершённой работы. Для частичного PR отдельно укажи остаток родительской Issue.

Если недостающий факт меняет выбор ближайшего действия, назови конкретный источник или вопрос и объясни зависимость. Если маршрут уже определён, передай недостающий факт исполнителю выбранного этапа. Например, после подтверждённого merge пробел по №12 или №13 входит в задание №14.

Размещай подсказку за пределами публикуемого артефакта и полного задания. Показывай команду для владельца и останавливайся после ответа.

Для проверки изменений правил используй [контрольные примеры](references/control-cases.md). При обычном вызове определяй шаг по источникам запрошенной задачи на выбранный момент.
