# Delivery

## Граница workflow

Каноническая последовательность:

`Issue → проверенное основание (durable Approved Plan или разрешённый N/A) → поручение на реализацию → refresh target branch → branch → implementation → self-review → checks → docs → final self-review → commit → push → Draft PR → PR sanity`

После PR sanity определи ближайшее действие по разделу «Передача результата реализации». Независимое ревью, Review fixes, Re-review и Human Merge Gate регулирует [trade-system-pr-review](../trade-system-pr-review/SKILL.md).

## Plan и Human Gate

До Plan изучи связанный Issue, `ROADMAP.md`, применимые `AGENTS.md` и path-specific instructions, ADR, contracts, релевантный код и подходящие skills. Plan должен определить компоненты, последовательность, архитектурные последствия, проверки, документацию, риски и границы scope.

Для нетривиальной задачи implementation запрещён до явного Human Gate — утверждения Plan человеком. Остановись и верни вопрос человеку при новом архитектурном выборе, scope expansion, конфликте Issue/Plan/ADR/contract или необходимости изменить согласованный `WHAT`.

Утверждение точного HOW завершает Human Gate. Публикуй только после разрешения владельца на публикацию утверждённой редакции. После публикации и проверки используй уже выданное применимое поручение на №6. Если разрешена только публикация, зафиксируй результат и предложи команду реализации. Так же разделяй утверждение, публикацию и поручение продолжить работу после Amendment. Одно сообщение владельца может содержать несколько явных разрешений.

На обычном маршруте до обновления target branch и создания branch:

1. Сохрани полный Approved Implementation Plan отдельным комментарием связанного GitHub Issue с точной первой строкой `# Approved Implementation Plan`; canonical comment должен быть опубликован `vbondarev` с `author_association=OWNER`.
2. Получи permalink комментария и проверь, что он доступен для чтения. При ошибке публикации или проверки остановись до исправления состояния.
3. Не редактируй base Plan или Amendment. После human decision, нового Human Gate и разрешения на публикацию создай отдельный append-only comment `# Approved Implementation Plan — Amendment` со ссылкой `Base Approved Implementation Plan: <permalink>` и только утверждённым изменением `HOW`.
4. Если canonical artifact изменён/удалён или effective HOW невозможно восстановить, остановись и запроси Human Decision.

### Передача плана

По совмещённому поручению после `ISSUE_PUBLISHED_VERIFIED` передай сверенный WHAT и источник полномочий в №4, если требуется обычный маршрут и базовый план ещё предстоит подготовить. Передай полную редакцию, паспорт, самопроверку и применимые правила независимому ревьюеру №5.1. После №5.2 передай исправленную редакцию, замечания, запись пакета и затронутые переходы для независимой перепроверки. Координатор проверяет результат и передаёт точную версию владельцу на №5.3. Общий для этапа лимит, учёт пакета, возобновление и остановку применяй по [правилам координации](../../../docs/development/README.md#работа-между-решениями-владельца). Поручение «покажи здесь» ограничивает продолжение.

### Сокращённый маршрут N/A

Для подтверждённой публикации Issue сначала установи наличие и состояние плана и поправок. Если данные неполны, укажи источник для сверки. Для точечного и проверяемого Issue без доверенных Approved Plan и Amendments примени `N/A`, только если владелец явно разрешил его для этого Issue до реализации. После разрешения предложи №6 с номером Issue и доказательством решения. Для запуска нужно явное поручение на реализацию. Если Issue подходит, а решения ещё нет, спроси владельца, разрешает ли он `N/A` или выбирает №4. Если нужен план, предложи №4, когда его предстоит подготовить, или первое оставшееся действие по существующему плану. Сохрани действующий permalink, в том числе для малого FIX.

На `N/A` используй требования и критерии Issue как основание исполнения, сохрани проверяемую ссылку на разрешение владельца и передай её на ревью. При росте объёма или существенном техническом выборе — STOP и обычный маршрут с базовым планом.

После проверки применимого основания и получения поручения на реализацию повторно получи актуальную target branch. Проверь существующие ветку и PR для нужной части плана, затем при необходимости создай `task/<issue>-<kebab-case>`. Ограничь работу согласованным WHAT и effective HOW или точечными требованиями Issue на разрешённом `N/A`.

## Implementation и проверки

Перед commit выполни основной self-review полного diff относительно target branch. Сверь реализацию с Issue и Approved Plan, архитектурными границами, backward compatibility, security/concurrency, tests, документацией, случайными файлами, debug-кодом и secrets; исправь подтверждённые замечания.

Выполни применимые checks. Неприменимые проверки не называй успешными и кратко укажи причину. Синхронизируй документы, ставшие неверными из-за реализации. После fixes/tests/docs проведи final self-review полного итогового diff.

## Commit, Draft PR и sanity check

- В PR description добавь permalink базового Approved Plan и permalink каждого применимого Amendment либо `- Нет`. Для разрешённого `N/A` укажи `Approved Implementation Plan: N/A`, `Approved Plan Amendments:` с `- Нет` и проверяемую ссылку на разрешение владельца.
- PR sanity check подтверждает Issue, основание исполнения, PR metadata и текущий head. Для планового маршрута проверь доверенность и неизменность base Plan и Amendments, ссылку поправок на base Plan и порядок Issue comments. Для `N/A` подтверди применимость, отсутствие доверенных плана и Amendments, связь с Issue и разрешение владельца.

- Commit message: `#<issue>: <текст на русском языке в прошедшем времени>`.
- PR title: `#<issue>: <краткое название на русском языке>`.
- PR description пиши по-русски; включи `Closes #<issue>`, фактическую реализацию, отклонения от Approved Plan или явное указание об их отсутствии, выполненные проверки, риски и намеренно исключённый scope.
- Заполни раздел «Ожидаемый результат слияния» в шаблоне Draft PR. Укажи ожидаемое действие с Issue, условие закрытия или остаток частичной поставки и ожидаемые статусы ROADMAP. При sanity check сверь эти сведения с Issue, основанием исполнения и diff. Закрытие Issue проверяется отдельно по №14.
- Pull Request наследует актуальные classification labels связанного Issue и не вводит другую классификацию самостоятельно. Если новая область означает scope expansion или новое architecture decision, остановись и верни вопрос на Human Gate до изменения Issue/labels.
- До External Review проверь base/head, branch name, commit message, PR title/body, `Closes`, совпадение labels с Issue, полный diff, случайные файлы и применимый CI.

## Передача результата реализации

После №6 и №7.5 передай Issue и PR при наличии, рабочую ветку, выполненный объём или незавершённый IMP, HEAD и SHA вершины целевой ветки, основание исполнения и результаты проверок. Для обычного маршрута укажи permalink базового плана и применимых Amendments. Для `N/A` приложи доказательство разрешения. Укажи применимый CI и открытые условия. Если текущий HEAD, PR или доказательство ещё недоступны, явно обозначь, чего не хватает.

Определи результат по фактическому состоянию и дай одно ближайшее действие. При незавершённой и остановленной реализации сначала укажи прерванное действие. Оцени готовность по проверкам после выполнения согласованного объёма. По уже выданному поручению координатор может принять пакет и продолжить разрешённую цепочку. При отдельном запуске №6 или №7.5 действует граница указанного этапа.

| Состояние | Результат и действие |
|---|---|
| Согласованный объём реализован, Draft PR прошёл sanity check, результаты обязательных проверок подтверждены для актуального состояния | `READY_FOR_EXTERNAL_REVIEW`. Дай готовую команду независимому ревьюеру с PR, Issue, версиями и ссылками на материалы. Выбери №8 для первичного ревью или применимый №10 с исходным отчётом для Re-review. |
| Реализация завершена, применимый обязательный CI ещё выполняется | `WAITING_FOR_CI`. Передай PR, Issue, HEAD, ветку и SHA её вершины, запуск, статус и применимое поручение на ожидание. При явном поручении координатор дожидается результата, перечитывает PR и вершину ветки и при подтверждённом CI актуальной пары передаёт результат в №8 либо применимый №10. Сбой, смену пары или окончание ожидания обработай по правилам координации. |
| Обязательная проверка завершилась ошибкой либо её результат или применимость не подтверждены | `BLOCKED_BY_VERIFICATION`. Назови упавшую проверку или недостающее доказательство, источник для сверки и ближайшее действие по причине блокировки. |
| Реализация остановлена на конкретном действии | `BLOCKED_BY_IMPLEMENTATION`. Укажи прерванный IMP или действие, источник препятствия и ближайший шаг. Если требуется выяснить допустимый способ продолжения или получить решение владельца, передай действие и источник в №7.1. |

Для №7.5 восстанови действующее основание, проверь доказательство устранения препятствия и поручение владельца. Возобнови конкретный незавершённый IMP в существующей ветке по действующему плану. Если работа остановилась снова, передай прерванное действие и последнее подтверждённое состояние, даже если нового HEAD или PR ещё нет. При остановке FIX, ревью или допуска верни работу к соответствующему этапу.
